# GM Locations — Phase 0 Functional Recovery

Branch: `claude/locations-context-contract-i8tbp0`
Scope: GM Datapad Locations surface only (`scripts/ui/shell/gm/GMLocationsSurfaceService.js`,
`scripts/ui/shell/gm/controllers/GMLocationsSurfaceController.js`,
`templates/shell/shell-surface.hbs`, `templates/apps/gm-datapad/surfaces/locations.hbs`).
No redesign, no new state/modal/wizard engine, no SWSE mechanics, no actor-sheet
or Phase 7 changes.

## 1. Executive verdict

**PHASE 0 COMPLETE WITH DOCUMENTED RUNTIME FOLLOW-UP.**

The suspected `surface` vs `shellSurfaceVm` context-contract mismatch was
**confirmed** and is the primary defect: `templates/shell/shell-surface.hbs`
rendered the Locations partial without passing `surface=shellSurfaceVm`, so
every `surface.*` expression in `locations.hbs` (all of them — the whole
template) resolved against `undefined`. A second, real defect was also
confirmed: `GMLocationsSurfaceService` discarded `state.modal.defaults`
generated by the Faction/Contact → Create Location handoff. Both are fixed
with one-line/small, surgical changes. No CSS change was needed or made —
no verified CSS defect blocks rendering, interaction, or footer reachability.

## 3. Context pipeline (as verified in source)

```
GMSurfaceRegistry.buildSurfaceVm({ surfaceId: 'locations', host })
    -> imports GMLocationsSurfaceService, calls buildViewModel(host)
    -> wraps the result: { id, surfaceId, ...vm }
        ↓
GMDatapad._loadPageContext(pageId)
    -> returns that wrapped object as `pageContext`
        ↓
GMDatapad._prepareContext()
    -> shellSurfaceVm: pageContext        (the VM, addressable as one object)
    -> ...pageContext                     (the SAME VM, also spread flat onto root context)
        ↓
templates/shell/shell-surface.hbs
    -> {{#if (eq shellSurface "gm-locations")}}
         {{> ".../locations.hbs" }}       <-- BEFORE FIX: no `surface=` passed
       {{/if}}
        ↓
templates/apps/gm-datapad/surfaces/locations.hbs
    -> reads surface.pageTitle, surface.locationManager.* throughout (452 lines, 50+ references)
```

`GMLocationsSurfaceService.buildViewModel()` returns exactly:
```js
{ pageTitle, pageDescription, locationManager: { filters, cards, allCards,
  selected, editor, modal, stats, library, leadQueue, ...option lists } }
```

## 4. Confirmed root cause

`shell-surface.hbs`'s `gm-locations` branch rendered the partial with **no
context parameter at all**:

```hbs
{{#if (eq shellSurface "gm-locations")}}
  {{> "systems/foundryvtt-swse/templates/apps/gm-datapad/surfaces/locations.hbs"}}
{{/if}}
```

Because a Handlebars partial invoked with no explicit hash arguments inherits
the *ambient* render context, `locations.hbs` was actually evaluating
`surface.pageTitle` etc. against the same context in which `shellSurfaceVm`
already lives as a *property named* `shellSurfaceVm` — not as `surface`. Every
`surface.*` path in the template therefore resolved to `undefined`, and
Handlebars silently renders `undefined` as empty string / falsy — no error,
no console warning, just empty counts, empty lists, and modals whose
`{{#if surface.locationManager.modal.isCreate}}` guard is permanently false.

This uniquely affects Locations: every other `gm-*` surface template in this
codebase (Factions, Intel, Jobs, Trade, etc.) is written against the
**flattened root context** (`{{pageTitle}}`, `{{intelManager.selected}}`,
etc.) rather than a `surface.*` prefix, which is why `...pageContext` being
spread onto the root context already made those surfaces work without an
explicit `surface=` binding. Locations is the one surface whose template was
authored against a `surface.*` convention that nothing in the shell actually
supplied.

**VERDICT: CONTRACT_MISMATCH_CONFIRMED.**

## 5. Template/service contract — before

| | Shape |
|---|---|
| Service return (`buildViewModel`) | `{ pageTitle, pageDescription, locationManager: {...} }` |
| Host page context (`_loadPageContext`) | `{ id: 'locations', surfaceId: 'locations', pageTitle, pageDescription, locationManager }` |
| `shellSurfaceVm` | same object as above |
| Partial invocation | no hash arguments — inherits ambient context |
| Template expects | `surface.pageTitle`, `surface.locationManager.*` |
| Result | `surface` undefined in the partial's context → every expression under it is `undefined` |

## 6. Template/service contract — after

Single change, `templates/shell/shell-surface.hbs`:

```hbs
{{#if (eq shellSurface "gm-locations")}}
  {{> "systems/foundryvtt-swse/templates/apps/gm-datapad/surfaces/locations.hbs"
      surface=shellSurfaceVm}}
{{/if}}
```

`surface` now resolves to the exact VM `GMLocationsSurfaceService.buildViewModel()`
produces. Statically and via an executed test (§15), the following all now
resolve against real data: `surface.pageTitle`, `surface.pageDescription`,
`surface.locationManager.stats`, `.library`, `.cards`, `.selected`, `.editor`,
`.modal`.

No other GM surface's partial invocation was touched — they already read the
flattened root context correctly and remain unchanged.

## 7. Modal open-state trace

**New Location:** `data-location-action="new"` → `GMLocationsSurfaceController`
sets `patchSurfaceState('locations', { selectedLocationId: '', modal: { type:
'create' } })` → `requestShellRender` → `GMLocationsSurfaceService` rebuilds
`locationManager.modal.isCreate = true` (`modalType === 'create'`) →
`{{#if surface.locationManager.modal.isCreate}}` (now resolvable) renders the
create wizard. **LIVE_HANDLED after fix** (was dead before: `surface`
undefined made the `{{#if}}` permanently false regardless of state).

**Import Location:** `data-location-action="open-import-modal"` → `modal: {
type: 'import' }` → `locationManager.modal.isImport = true` →
`{{#if surface.locationManager.modal.isImport}}` renders the import wizard.
Same before/after status as New Location.

**Edit Location:** `data-location-action="edit"` → `selectedLocationId` is
retained (not cleared) and `modal.type = 'create'` → because `selected` is
truthy, `GMLocationsSurfaceService` sets `editor = selected` (the full
existing record, via `selectedVm()`), not a blank editor → the create wizard
template (shared markup for both new+edit) renders with the existing values
already filled in (`surface.locationManager.editor.name`, `.raw.region`,
etc.). Confirmed by direct code read, not assumed from selector presence.

`ShellSurfaceState.patch()` (verified in `scripts/ui/shell/ShellSurfaceState.js`)
does a **shallow, top-level merge** per surface: `{ ...current, ...patch }`.
Setting `modal: { type: 'create' }` therefore fully replaces the previous
`modal` value (no partial-object leakage), which matters for §10 below.

## 8. Create wizard trace

4 pages (`data-wizard-page="1..4"`: Identity, Placement, Visibility, Notes),
driven by `GMLocationsSurfaceController._wireWizardControls()` /
`_shiftWizardPage()` / `_setWizardPage()` operating purely on the wizard's
own DOM subtree (`wizard.dataset.currentPage`, `.is-active` toggling,
back/next `disabled` state, Next button relabeled "Review Complete" on the
last page). `wizard-next`/`wizard-back` do **not** call `patchSurfaceState`
or trigger a re-render — they mutate the already-rendered DOM directly, so
normal Next/Back navigation cannot itself cause a rerender that resets the
wizard to page 1. Confirmed via `tests/gm-datapad-wizard-contract.test.mjs`
(pre-existing, unmodified) at the template/controller selector-agreement
level, and via direct code read for the execution-level claim above (this
codebase's Foundry-absolute-import convention on the controller file makes
it a Node-execution test candidate but that file already documents why it is
scanned statically instead — see that test's header comment).

Save path: `form[data-location-form]` submit → `locationPayload(FormData)` →
`LocationRegistryService.upsertLocation()` → on success,
`patchSurfaceState('locations', { selectedLocationId: location.id, modal:
null })` → re-render closes the modal and selects the new/edited record.

## 9. Import wizard trace

3 pages (Browse, Options, Import). `Import Selected` is a `type="submit"`

`GMLocationsSurfaceController._wireForms()` →

## 10. Faction/contact prefill trace

`GMFactionRelationshipSurfaceController`'s `create-location-faction` /
`create-location-contact` actions call:

```js
this.host.patchSurfaceState?.('locations', {
  modal: { type: 'create', defaults: { name, controllingFactionId, factionIds, contactIds, publicSummary } }
}, { render: false });
await this.host._navigateTo('locations');
```

**Confirmed defect:** `GMLocationsSurfaceService` built the editor as
`const editor = selected || blankEditorVm();` — `state.modal.defaults` was
read nowhere. `GMIntelSurfaceService` already has the correct pattern for
this exact situation (`editorFromRecord(selectedRecord, selectedRecord ? {}
: modalDefaults)`), used as the model for the fix.

**Fix:** added `applyCreateDefaults(editor, defaults)` in
`GMLocationsSurfaceService.js`, applied only in the no-selection branch:

```js
const editor = selected || applyCreateDefaults(blankEditorVm(), rawModal.defaults);
```

It copies `name`, `controllingFactionId` (into `editor.raw`), `factionIdsText`
/ `contactIdsText` (via the existing `tagsLabel()` helper), and
`publicSummary` (into `editor.raw`) — the exact fields the Faction/Contact
handoff supplies — falling back to the blank editor's own value when a field
is absent. Editing an existing location always takes the `selected` branch,
so defaults can never apply to an edit. Because `ShellSurfaceState.patch()`
fully replaces `modal` on every subsequent action (§7), a later plain "New
Location" click's `modal: { type: 'create' }` (no `defaults` key) cannot
inherit stale defaults from a prior Faction/Contact handoff.

## 17. Remaining Locations defects (known, not fixed in Phase 0)

1. **Atlas-lead-queue and encounter-seed/scene UI is computed but not
   rendered.** `locationManager.leadQueue`, `selected.encounterSeeds`,
   `selected.sceneRows` exist in the VM and `GMLocationsSurfaceController`
   has live handlers for `lead-*`, `remove-seed`, `remove-link`,
   `create-encounter-scene`, `activate-scene` — but `locations.hbs` renders
   no markup that triggers any of them. Not a regression; pre-existing scope
   gap. Fixing it means adding template markup, which is out of Phase 0's
   "don't rewrite the template" boundary.
2. **Wizard-reset-on-unrelated-rerender is theoretically possible but not
   demonstrated reproducible.** `_wireWizardControls()` calls
   `_setWizardPage(wizard, 1)` on every controller `attach()`, which runs on
   every full shell re-render. Ordinary Next/Back does not trigger a
   re-render (§8), so normal wizard use is not affected. No currently-wired
   action fires a re-render while a wizard modal is open and the user is
   mid-wizard (filter inputs live outside the modal; modal-internal actions
   like `wizard-next`/`wizard-back` don't re-render) — so this was not
   reproducible from the current control flow and, per Phase 0 rules, was
   left undisturbed rather than "fixed" speculatively.
3. **Modal runtime geometry** (via `GMInteractionRepairService`) was not
   touched — no verified CSS/layout defect was found for Locations
   specifically, and Phase 0N explicitly reserves CSS changes for a proven
   functional defect only.
4. Registry save/reveal/delete round-trips (§11) are verified by source
   reading and by the read-side VM tests, not by an actual write against a
   live Foundry `game.settings` document store — see the manual checklist.
