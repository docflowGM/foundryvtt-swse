## 3. Changes
### 3.1 TX-11 — `runFollowerMutationTransaction` failure-value contract
A `commit` or `rollback` outcome counts as **failed** when it throws, returns the boolean `false`, or returns an object with `ok === false` or `success === false`. Everything else (undefined, `true`, a document, a plain object, `0`, `null`, a string) is success — the previous contract for every existing step. A reported commit failure rolls back the *earlier* steps and never runs later ones (the failing step itself is not rolled back, exactly like a thrown one); a reported rollback failure sets `rollbackFailed` and is listed in `rollbackErrors`. No existing step returns a failure value, so no current behavior changes; the full suite confirms it.
### 3.2 TI-N5 — rollback outcome reaches the caller
`assignAsAlly`, `unassignAlly` and `convertToFollower` throw the **original error, message unchanged**, annotated with `failedStep`, `rollbackFailed` (strict boolean) and `rollbackErrors`. Assign/unassign now log at `error` level ("rollback INCOMPLETE, manual review required") instead of the unconditional "failed and was rolled back" when it was not. The existing `convertToFollower` reservation-cleanup logging is unchanged.
### 3.3 TX-10a — the asset-state check is part of the approval transaction
`TransactionEngine.executeAssetApprovalTransaction` refuses, **inside its lock and before any write**, an asset that already carries a store-acquisition record (`system.storeAcquisition.transactionId`, the same marker the approval itself writes): `{ success:false, refused:'already-acquired', acquiredTransactionId }`, owner not charged, nothing changed. This makes every re-approval path (stale queue entry, retry after an unrelated post-commit failure, second client) safe against a double charge.
### 3.4 TX-10b/c/d — GM approvals service and surface
* **a. Stable action keys.** The surface already exposed `stableKey` (`custom-id:<id>`) for *selection continuity* only; the mutation buttons still read `selectedApproval.key` (`custom:<index>`). Each request now also carries `actionKey` (`stableKey || key`) and the nine `data-approval-key` bindings on the approve / deny / edit / finalize buttons read it. `parseApprovalKey` understands `custom-id:<id>`; `resolveCustomIndex` resolves the **current** queue index at the moment of the action, and an id no longer in the queue resolves to `-1` ("no longer pending") — never to whatever record now occupies the old slot. Legacy `custom:<index>` keys still parse. Selection keys are unchanged (`key` is pinned by an existing test).
* **b. Deny guard.** A draft that already has a store-acquisition record is an owned asset, not a draft: deny removes only the stale queue entry (warning to the GM) and **keeps the asset**. Genuine pending drafts are deleted as before.
* **c. Post-commit isolation.** After `executeAssetApprovalTransaction` / `StoreEngine.purchase` reports success, the history mirror, queue removal, `swseCustomPurchaseApproved` / `swseApprovalResolved` hooks, refresh and notification run through `_afterCommit`: a failure is a *warning* ("…the approval itself is committed; do not approve it again"), never "Failed to approve". Combined with §3.3 a retry cannot charge twice.
### 3.5 TX-09 sub-gap — `ProgressionFinalizer._applyMutationPlan`
Plan application and post-apply bookkeeping are separate `try` blocks. A plan failure is still `{ success:false, error }` (and skips the sync). A post-apply sync failure after a **committed** plan is `{ success:true, postApplyWarnings:[{ step:'post-apply-sync', error }] }`, logged at `error`, with a GM/player notice not to finalize again; `finalize` and `finalizeSingleStep` pass the warnings through. The level-up post-audit failure keeps `success:false` (the audit disagrees with the result) and now carries `committed:true`. `_emitLevelUpComplete` already isolated its own failures.
### 3.6 TX-07(a) — wording
"Atomic" claims on sequential, non-multi-document paths were corrected to the real guarantee in `transaction-engine.js` (header), `store-engine.js` (header and `purchase()` doc), `ally-assignment-service.js` (module and `convertToFollower` docs), `droid-/vehicle-customization-engine.js` and `GMApprovalOperationsService.approveDroid`. Remaining inline "atomic" comments in `ally-assignment-service.js` step bodies, `follower-creator.js` and the transactional progression/lightsaber callers were left (no behavior depends on them); the project-wide static wording guard is TI-4.

## 8. Independent-review corrections (TI3-R1, R2, R3) — reviewed head `e325415`
All three were reproduced against `e325415` with deterministic tests (§4 now has 10 checks; the original eight are unchanged apart from two fixture corrections noted in §8.5) and fixed on this branch. L1, offline.
### 8.1 TI3-R1 — strict approval identity
**Defect (reproduced):** `_findApprovalIndexById` searched by id but fell back to the old queue index when the id was missing, so after an approval's own entry had been removed by another operation (and another request had slid into its slot) the post-commit cleanup removed the **unrelated** request.
**Fix:** a record with an id is found by that id or **not at all** (`-1`); an id-less legacy record may use its old index only while the entry there is **byte-identical** to the record (the one way its identity can be established), otherwise `-1`. New `isStillPending(approval)` uses the same rule.
**Tests (§3.6):** (a) removing a gone id by a stale index removes nothing and leaves the request now in that slot; (b) end to end — another GM removes request A *while A's approval transaction runs*, B shifts into index 0, A's cleanup leaves B in the queue and B is not approved; (c) legacy id-less records: identical-entry fallback works, a different record in the slot is not removed.
### 8.2 TI3-R2 — destructive denial
**Defects (reproduced):** (i) a legacy `custom:<index>` deny deleted whatever actor the request now at that index named; (ii) the acquired-marker check and `draftActor.delete()` were not exclusive with an approval of the same asset; (iii) a draft whose pending state could not be confirmed was deleted anyway; (iv) a **second, reachable approvals UI** — `GMStoreDashboard` (settings menu `core/settings.js`, sidebar launcher `actor-sidebar-controls.js`) — deleted the draft addressed by its rendered `data-index` with no revalidation, and approved by rendered index.
**Fix:** one shared core, `GMApprovalOperationsService.decideDenial({ approvalId | index, host })`, used by the shell service **and** the dashboard:
* **Identity:** an index cannot identify an id-bearing record → `ambiguous`, nothing deleted. An id that left the queue → `missing`.
* **Coordination boundary (L1):** the decision takes `TransactionEngine.acquireAssetDecisionLock(ownerId, draftId)` — the **same lock key** `executeAssetApprovalTransaction` takes — so an approval in flight makes the denial `busy` (nothing deleted) and a denial in flight makes an approval "already in progress". Everything below is re-read **under the lock**, immediately before the delete.
* **Revalidation under the lock:** queue membership (strict id), acquisition state (acquired → only the stale entry is removed, asset kept: `stale-approved`) and pending state — the draft must still carry the markers the store checkout writes and approval clears (`flags.foundryvtt-swse.draftOnly` / `pendingApproval`, or `system.storeAcquisition.pendingApproval`); a draft that is neither acquired nor confirmably pending → `uncertain`: **not deleted**, request left queued for manual review.
* The dashboard's deny now calls the same core (its own delete is gone, pinned by a source test), its approve first requires `isStillPending(approval)`, and its denied-hook is isolated like the shell's.
**Stated limit:** the lock is process-local (same client); another client or a direct document delete is not coordinated, and the check-and-delete has no compare-and-swap (the pending check and `delete()` are adjacent with no `await` between them). The `custom:<index>` form is still *accepted* for **approve** (the engine's already-acquired refusal and the lock protect against a double charge, but a stale index could still approve the wrong *pending* request); only the destructive operation was made fail-closed. Tightening approve the same way is a small follow-up if you want it.
**Tests (§3.7):** ambiguous index; queue changed between the first read and the lock (request gone, neighbor untouched); approval in flight → denial refused, then the approval commits and charges once; unconfirmable draft kept; dashboard source pins.
### 8.3 TI3-R3 — incomplete progression synchronization
**Category established:** `system.starshipManeuverSuite.maneuvers` / `.max` is **persisted character state** (the sheet's "Active Suite (n/max)", the maneuver step and the suite lifecycle hook all read it), not presentation.
**Fix:** a committed plan followed by a failed suite sync returns `{ success:true, committed:true, postApplyIncomplete:true, postApplyWarnings:[{ step, field:'system.starshipManeuverSuite', error, repair }], postApplyRepair:{ starshipManeuverNames, starshipManeuverRemoveItemIds } }` (propagated by `finalize` and `finalizeSingleStep`); a clean finalization carries `committed:true` and **no** incomplete flag; the level-up audit failure keeps `committed:true`. **`ProgressionFinalizer.resyncPostApplyState(actor, repair)`** repairs only that state: it re-runs the suite synchronization — it never calls `applyMutationPlan`, so no feat, talent, attribute, HP or other grant is replayed and nothing is spent twice. `_syncPostApplyState` is now **idempotent** (the result is a set derived from the actor's items; nothing is written when the persisted suite already equals it) and returns `{ changed }`. A failing repair returns `{ success:false, error }` (never throws).
**Tests (§3.5, extended):** incomplete flags and repair payload; the repair issues zero plan applications and exactly one write touching only the two suite fields; a second and third resync write nothing and create no duplicate; removal ids are idempotent; a failing repair reports; a clean finalization has no incomplete flag. No UI button for the repair is added in this pass (the notice names `resyncPostApplyState`); wiring one is a follow-up.

## 6. Limits and residual risk (stated, not hidden)
* Same client only (L1). Two GMs on two machines, or a writer outside these services, are not coordinated; the engine's already-acquired refusal and the id-addressed keys *narrow* the damage of a cross-client race but cannot serialize it.
* `convertToFollower`/`assignAsAlly` step rollbacks still write **absolute** prior values (e.g. `system.ownedActors`), so a concurrent change to that list inside the failure window is overwritten (ledger TX-11, unchanged — an existing test pins "exact pre-commit array" rollback).
* The follower-creator's multi-step flows were not re-engineered; they already consult `rollbackFailed`.
* Foundry runtime, durable replay (operation ids) and multi-client arbitration remain outside scope (TI-4 / runtime certification).
