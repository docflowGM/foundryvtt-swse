# Equipment Ecosystem E0 — Producer / Consumer Matrix

**Status:** E0 research deliverable. Documentation only. No production code, data, schema, test or tool was changed.
**Base commit audited:** `185dac1bded12f5e40cb851539c0a912f42fc24d` (see `equipment-ecosystem-e0-baseline.md` §1 for the upstream-divergence note).
**Authority for scope:** the "Universal Equipment Ecosystem — Master Implementation Directive and E0–E1 Execution Authorization".

## 0. How to read this document

- Everything in this document describes **current repository behaviour**, established by static reading of the cited lines. Nothing here was exercised in Foundry; "runtime" claims are explicitly marked *static read only*.
- "Planned future phase" names the phase of the **approved roadmap** in which the row would be touched. It is a planning label, not an authorization (only E0–E1 are authorized).
- "Test" is the result of searching `tests/*.mjs` for the module/symbol name. A named test means a test *references* the symbol, not that every branch of the row is covered. `GAP` means no test referencing the module/symbol was found. File-reference counts are given as `refs=N` where a name-only search was used.
- `ALIAS` = one of the equip-state aliases listed in §2. `FS` = `flags.swse.fireState`.
- **Authority** = the module that currently owns the rule or the write. "None" means the read is an independent copy of an equip predicate with no owner.

Legend for the *Current established meaning* column: **DRAWN** = in the actor's hand/ready for use (the semantics `InventoryEngine.setWeaponReadied` gives `equipped` for weapons); **WORN** = armor/equipment worn/carried; **ACTIVE** = powered/operating (independent in the approved design, but conflated with equip in several readers — see §2).

## 1. Headline finding (read this first)

**Today, for ordinary weapons, `system.equipped` already means "drawn/readied", not "held-but-not-ready".**

`InventoryEngine.toggleEquip` sends every weapon to `toggleWeaponReadied` (`scripts/engine/inventory/InventoryEngine.js:70-74`); `setWeaponReadied` charges a Move action (Swift with the Quick Draw metadata) and writes the alias set through `equipMirrors` (`InventoryEngine.js:212-237`, `39-54`). The sheet labels the same state "Drawn"/"Stowed" (`scripts/sheets/v2/character-sheet/concept-context.js:346-376`).

There is **no representation of the approved EQUIPPED posture** (physically held, not in a validated configuration) anywhere in the repository, and **no representation of hand occupancy**. The existing `wielded: 'one-handed'|'two-handed'` value in `FS` is the player's *grip choice*, not an occupancy record (`scripts/items/weapon-runtime/owned-state.js:3-17`, `resolveWielding` at `:45-`).

Consequence for the roadmap: the legacy value `equipped === true` on a weapon has to be mapped to exactly one of the new postures by an explicit owner decision (see authority contract §E1.2, `OWNER_APPROVAL_REQUIRED` item OA-1). The matrix below shows 30+ readers whose behaviour depends on that mapping.

## 2. Equip-state alias census (the ambiguity, enumerated)

`isItemEquipped()` (`scripts/items/weapon-branch-resolver.js:729-742`) is the repository's canonical "is this equipped/drawn" predicate. It returns true if **any** of these is truthy (truthiness is `isTruthyEquipState`, `:641-649`, which also accepts the strings `equipped, worn, held, readied, ready, on, active, natural`):

| # | Field / source | Notes |
|---|---|---|
| 1 | `system.equipped` | primary field; schema default `false` (`template.json:602`) |
| 2 | `system.isEquipped` | legacy alias |
| 3 | `system.active` | **activation, not posture** — included by the canonical predicate |
| 4 | `system.readied` | legacy alias |
| 5 | `system.equippable.equipped` | nested alias (set on starter lightsabers, `progression-finalizer.js:2987`, `:3109`) |
| 6 | `system.equippable.active` | nested activation-flavoured alias |
| 7 | `system.activation.active` | nested activation |
| 8 | `flags.swse.equipped` | flag alias |
| 9 | auto-equipped natural weapon (`flags.swse.autoEquipped`/`alwaysArmed`) | `weapon-branch-resolver.js:658-663` |
| 10 | integrated droid weapon (`system.integrated`/`droidIntegrated`/`flags.swse.integrated` on a droid) | `:707-714` |

Additional equip signals read by *other* predicates (not by `isItemEquipped`): `system.activated` (CombatEngine, character-like-sheet), `system.equipStatus`/`system.status`/`system.state` (CombatEngine, character-like-sheet, combat-stat-rules), `system.carried` (WeaponVisualProfileResolver), `system.carried.equipped`/`system.location` (suggestion engine), `system.worn`/`system.active` (force-alchemy).

**Writers cover fewer aliases than readers.** `equipMirrors` only writes an alias if the field already exists on the item (`!== undefined` guards, `InventoryEngine.js:41-48`), always writes `system.equipped`, and on stow additionally clears `system.active` and `system.activation.active`. It never writes `system.equipStatus/status/state/carried`.

## 3. Reader-predicate divergence (hazard H-01)

The same question — "is this weapon equipped?" — is answered by **at least eight different predicates**. They agree only when the item carries exactly the aliases the writer maintains.

## 6. Highest-risk coupling points (summary for the owner)

1. **R-1 — `isItemEquipped` couples posture and activation** (`system.active`, `equippable.active`, `activation.active` satisfy "equipped"). Separating EQUIPPED from READIED *and* keeping activation independent requires splitting this predicate (C1, C2, C4, A5).
2. **R-2 — Eight-plus divergent reader predicates (§3).** A staged migration needs a per-reader disposition; narrow readers (D3, D4, D6, D10) will not follow a change to the canonical predicate.
3. **R-3 — Writers and readers disagree about which aliases exist** (A1, A2, A14 vs D10). Alias fan-out is conditional; the nested `equippable.equipped` is read alone by `weapons-engine` yet is written alone by the crystal system.
4. **R-4 — No hand-occupancy record.** `wielded` is a grip *choice*; `isOffhand`/`slot` is a designation; `heldTogetherIds` models one specific rule. None records which manipulator holds what. (E3 adds this; today nothing to migrate, but nothing to validate against either.)
5. **R-5 — Armor equip has no action cost and does not use `equipMirrors`** (A2). Directive §2 requires that armor donning/removal not be bypassed by an instantaneous toggle; today's `toggleEquip` is that toggle. Whether this is intended current behaviour is an owner/rules question (SRC-2 in the authority contract), not something this phase changes.
6. **R-6 — Attack path is not gated on drawn state in `attacks.js` / direct-id `CombatEngine` resolution** (D1, D2). Static read only.
7. **R-7 — Cache keys** (E6, F2, F3) hash `equipped`-family fields but not `FS`; new posture/occupancy state needs explicit invalidation keys.
8. **R-8 — Light-sync hook** (A16) enumerates watched fields by name.
9. **R-9 — Creation-time producers** (A15) birth items as `equipped: true`; a legacy-mapping decision (OA-1) changes how every existing starter lightsaber, natural weapon and droid-integrated weapon is interpreted.
