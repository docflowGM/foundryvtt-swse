## Governing requirement

> If a player sees a number in a character sheet box, weapon card,
> tooltip, roll dialog, or chat result, we must be able to prove exactly
> why that number exists.

Target shape: `persisted inputs → ONE domain authority → contribution
ledger → derived/static result → sheet/tooltip/roll consumer`.

## Site classification key

- **A** — canonical calculation authority
- **B** — legitimate consumer
- **C** — legitimate contextual resolver
- **D** — duplicate/reimplemented formula
- **E** — compatibility fallback
- **F** — dead/unreachable
- **G** — UI reconstruction
- **H** — unknown / needs tracing

## Batch 1 certification correction, round 2 (post-review): Grapple SSOT was still not actually true

A third review found that round 1's Grapple fix, despite being described as achieving "one grapple formula," still had **two independent implementations**: the new `resolveGrappleBonus(actor)` resolver, and `derived-calculator.js`'s own inline grapple block, which round 1 never touched. They agreed numerically, but per the freeze charter, agreement is not the standard — a single arithmetic authority is. **Fixed**: extracted the arithmetic itself into `combat-stat-rules.js#computeGrappleBonus({bab, strMod, dexMod, sizeMod, speciesBonus})`; both `resolveGrappleBonus(actor)` and `derived-calculator.js` now call this one function rather than each computing the formula independently. This also surfaced and fixed an unrelated, previously-invisible bug: `derived-calculator.js`'s old `bab.total` read was always `undefined` (`BABCalculator.calculate()` returns a plain number, never an object), so the canonical `system.derived.grappleBonus` was always `NaN` — silently masked by a sheet-side `Number.isFinite()` guard falling back to its own correct duplicate formula. New parity test (`tests/grapple-bonus-ssot-parity.test.mjs`) proves the four call sites (`computeGrappleBonus`, `DerivedCalculator`, `resolveGrappleBonus`, the actual roll formula) cannot disagree, across 5 input combinations, because they are now the same function rather than four functions that happen to agree today.

**Wording standard going forward**: "one grapple formula" is only claimed in this document once every consumer demonstrably calls the same function — not merely produces the same output. That standard is now met for Grapple.

## Batch 1 certification correction, round 3 (post-review): SSOT was true, but the single source itself was wrong, and two more consumers still bypassed it

A fourth review found that round 2's SSOT extraction, while a genuine architectural improvement, had certified agreement without ever checking the underlying constant against a published rule — and separately, that "SSOT" itself was still not complete: two more live consumers (the character sheet's displayed Grapple box, and the actual opposed-combat-check engine) were still independently reconstructing the formula rather than reading the canonical value. Three fixes, all detailed in the Grapple domain section's "Certification-correction addendum 3":

1. **`GRAPPLE_SIZE_MODIFIERS` was wrong.** Round 2 centralized a step-of-4 table (`fine:-8 … colossal:+16`) that had simply been copied forward from the original inline formula, with no citation and no check against the actual rule. Cross-validated against two real creature stat blocks already in this repo's compendium data (Aiwha, Bantha) and two independent rules-reference lookups: the correct table is step-of-5 (`fine:-20 … colossal:+20`). Fixed, with golden tests for all 9 categories plus the Aiwha/Bantha cross-check (`tests/grapple-size-modifier-book-values.test.mjs`).
2. **`PanelContextBuilder`'s displayed Grapple box and `SWSEGrappling._rollGrappleBonus()` (the opposed-combat-check base) were still each independently reconstructing the formula**, not reading the canonical value — the sheet box could silently discard a legitimate canonical `0`, and the opposed-check engine added a half-heroic-level term the published rule doesn't have, on top of a *third* independently-wrong size table. Both fixed to read `system.derived.grappleBonus`/`resolveGrappleBonus(actor)` and add only genuinely contextual bonuses on top.
3. **Repository-wide search found a fourth, previously unclassified duplicate**: `combat-stats-tooltip.js`'s Grapple hover-breakdown (STR-only, a fourth wrong size table, a dead miscMod field, no species-bonus row). Fixed. Every other remaining occurrence found in the search was classified (legitimate passthrough consumers, an out-of-scope data-authoring tool, two confirmed-but-deferred chargen/follower-preview defects recommended for Batch 2, and one newly-discovered modifier-pipeline wiring question flagged for a future audit) — see the Grapple domain section for the full list.

The parity test now covers 6 live consumers across 6 input combinations (`tests/grapple-bonus-ssot-parity.test.mjs`), and a new book-value golden test protects the size table itself against a future silent edit (`tests/grapple-size-modifier-book-values.test.mjs`).

**Wording standard, reaffirmed**: "one grapple formula" requires every consumer to call the same function; **"rules-fidelity-certified" additionally requires that function's constants to have been checked against a published source**. Both are now true for Grapple — this is the first domain in this freeze certified to both standards.

## Batch 1 certification correction, round 4 (post-review): the core formula was correct, but permanent static bonuses never reached it

A fifth review pointed out that round 3 certified the Grapple *arithmetic* without auditing whether every legitimate bonus source actually feeds it. The "Enslaved" background's "Grapple Survivor" (+2 competence, permanent, not mode-gated) was traced end-to-end through the real background pipeline and found to never reach a character's Grapple total at all, for two independent, interacting reasons — full detail in the Grapple domain section's "Certification-correction addendum 4":

1. **Duplicate representation at the source.** Enslaved's raw authoring data (`data/backgrounds.json`) describes the same +2 grant twice (`mechanicalEffect` and `specialAbilities[0]`), and `BackgroundGrantLedgerBuilder._mergeBonuses()` faithfully turned that into two ledger entries for one real grant.
2. **The consumer silently dropped it entirely, independent of (1).** `ModifierEngine._getBackgroundModifiers()`'s flat-bonus loop required every record to have `applicableSkills` (a skill-bonus-only shape) — Enslaved's `target:'grapple'`-shaped records always failed that guard and were silently skipped. Live-verified via the real pipeline: the +2 was authored, merged (twice), and materialized onto the actor — then discarded at the last step.

**The named trap, and why fix order mattered**: fixing (2) alone would have turned a silently-missing +2 into a silently-wrong +4. Fixed in the correct order — semantic-identity dedup at the ledger-builder level first, then generic target-shaped bonus support in `ModifierEngine`, with its own *defensive* dedup so an actor whose flags were already materialized with a stale duplicate (persisted before fix #1 existed) is still protected.

Also required and completed this round: an explicit static-vs-contextual audit of every `GRAPPLE_BONUS`-shaped source. Species and background bonuses are static (now correctly layered into `system.derived.grappleBonus` exactly once, via the same `modifierMap` every other domain already uses). Expert Grappler and Grapple Resistance are genuinely contextual (mode-gated in their own authored data) and were already correctly excluded from the static total since round 3 — confirmed directly against their compendium data, not assumed. A separate, pre-existing bug was found and fixed while wiring the tooltip: `combat-stats-tooltip.js#_getModifiersForTarget()` read the wrong storage path and had always returned no rows for any target, so `getGrappleBreakdown()`'s "SUM(rows) === total" invariant was previously untested and untrue in principle — now proven directly.

**New test**: `tests/grapple-static-modifier-composition.test.mjs` — 6 static-composition golden cases (including a pre-fix duplicate-representation input), Expert Grappler and Grapple Resistance contextual-boundary checks, and a real-pipeline reproduction (`hydrateBackgroundEvent` → `BackgroundGrantLedgerBuilder` → `applyCanonicalBackgroundsToActor` → `ModifierEngine`) confirming exactly one +2 grapple contribution reaches the modifier engine.

**Wording standard, extended**: "static-modifier-composition-certified" requires every static source to be traced from its authoring data to the canonical total and confirmed to arrive exactly once, every contextual source confirmed to never leak into that total, and the tooltip's displayed parts proven (not asserted) to sum to its displayed total. All three are now true for Grapple.

## Batch 1 certification correction, round 5 (post-review): static and contextual modifiers were composed in two separate stacking universes

A sixth review found the one remaining defect in round 4's design. `_rollGrappleBonus()` combined the static total and the contextual total as two plain numbers, which discarded each contribution's bonus `type` before the two sides ever met — so a contextual bonus of the *same* stacking type as a static one (e.g. Expert Grappler's contextual +2 competence alongside Enslaved's static +2 competence) could add on top of it instead of being capped by this codebase's own rule (`ModifierUtils.STACKING_RULES.competence === 'highestOnly'`). Live-reproduced exactly as described: the combination rolled +4 in an `attackGrapple` check where RAW says +2.

**Fixed**: contextual Grapple contributions are now collected as modifier **objects** (`collectContextualGrappleModifiers()`, replacing the number-returning `swseTalentGrappleBonus()`), unioned with the actor's already-resolved static modifier objects (`system.derived.modifiers.breakdown.grapple.applied`), and resolved together through `ModifierUtils.resolveStacking()` — the same shared authority every other domain in this codebase uses, not a hand-coded rule inside the Grapple system. The core term (which never stacks against anything) is read separately from the explicit `system.derived.grappleBonusParts.core` breakdown round 4 introduced.

**Wording standard, extended again**: "stacking-certified" requires every contextual contribution to be proven combined with the static contributions through the shared stacking authority — not added as a bare number — across same-type collisions in both directions and at least one cross-type case. That is now true for Grapple.

## Batch 1 certification correction, round 6 (post-review): a feat's rule metadata was itself semantically wrong, and the Grab attack read the wrong Reflex Defense entirely

A seventh review, reading the real, current `packs/feats.db` data rather than a synthetic fixture, found two further confirmed defects at the boundary between Grapple's already-certified modifier arithmetic and target-defense metadata correctness. First, `RESIST_GRAB_AND_GRAPPLE` bundled two different SWSE mechanics (a Reflex-Defense-vs-incoming-Grab bonus and an opposed-Grapple-check bonus) into one `bonus` field; Grapple Resistance grants both (coincidentally the same value), but Grab Back grants only the Reflex channel — so round 5's `collectContextualGrappleModifiers()` incorrectly credited a Grab Back defender with an opposed-check bonus that feat does not have. Second, `SWSEGrappling.attemptGrab()` read target Reflex via a fallback chain (`target.system?.defenses?.reflex?.total ?? ... ?? 10`) that the V2 pipeline never populates, silently collapsing to a hardcoded `10` for any real V2 PC, and duplicated a hit computation `SWSERoll.rollAttack()`/`AttackOutcomeResolver` already performs canonically.

**Fixed**: the channels were split explicitly in the rule shape itself (`GRAB_GRAPPLE_RESISTANCE: {reflexBonus, opposedGrappleBonus}`), migrated across all three live data sources (`packs/feats.db`, `packs/feat-catalog.db`, `data/feat-catalog.json`) and both normalization hooks, rather than special-casing either feat's name in consuming code. `attemptGrab()` no longer recomputes hit/miss — the Grab-specific Reflex bonus is passed into `rollAttack()` via a new, additive, opt-in `targetContext.defenseAdjustment` option (defaults to `0`, zero effect on existing callers), so the canonical resolver computes the hit once. A pre-existing, out-of-scope priority-order inconsistency between `attacks.js#getTargetReflex()` and `SchemaAdapters.getDefenseTotal()` was flagged rather than fixed in this round — see round 7 below, which fixes it. Full detail, including the required real-pack-data test coverage, is in the Grapple domain section's "Certification-correction addendum 6".

**Wording standard, extended**: "defense-context-certified" requires a feat's Reflex-vs-opposed-check channels to be split at the data/rule-shape level (never special-cased by name) and the Grab attack itself to delegate hit/miss to the canonical attack-outcome authority against the real derived Reflex Defense. Both are now true for Grapple.

## Batch 1 certification correction, round 7 (post-review): opposed-check ties, a bogus flat Reflex penalty on grapple states, and the target-defense priority-order inconsistency round 6 deferred

An eighth review confirmed round 6's fixes and round 5's stacking arithmetic are sound, but found the Grapple domain could not yet be called fully certified: three further live calculation/rules defects, plus one normalization completeness gap. (1) Opposed Grapple ties resolved backwards — SWSE's "meets or beats" rule means the attacker should succeed on a tie, but `grappleCheck()`/`_opposedGrappleForManeuver()` used a strict `>` and additionally short-circuited ties with no state change at all, exactly as already flagged in this repository's own pre-existing `docs/audits/combat-phase-0f-grapple-ion-seam-ledger.json`. (2) Grabbed/Grappled/Pinned applied a flat `-5 Reflex Defense` penalty that appears in no published rule and that `DefenseCalculator`'s canonical Reflex total does not even read as an input; the real rule is that Grabbed/Grappled carry no Reflex penalty at all, and Pinned removes only the actor's positive Dexterity bonus. (3) `attacks.js`'s target-defense priority order — flagged in round 6 as confirmed-but-deferred — was fixed rather than left deferred further, since it is a live authority violation for every attack in the game, not just Grapple; a related untruthful `defenseAdjustment` audit-trail hardcode was fixed alongside it. (4) Both Grab Back normalization fallbacks still granted only the reaction rule, never the +2 Reflex bonus, for a bare/legacy item.

**Fixed**: a single shared decision authority (`resolveOpposedGrappleOutcome()`) for every opposed Grapple check; all three grapple states' ActiveEffect Reflex changes removed, with Pin's real, component-aware Dex-bonus removal computed directly in `DefenseCalculator.calculate()` via a new dependency-free leaf module (`grapple-state-query.js`) shared with `GrappleStateEngine`; `attacks.js#getTargetReflex()`/`getTargetDefense()` made derived-first for Reflex/Fortitude/Will, matching `SchemaAdapters.getDefenseTotal()`, with `roll.swseAttackContext.defenseAdjustment` now reporting the real applied value; and both Grab Back fallback normalization paths updated to grant both rules. The repository's own pre-existing Grapple audit (`combat-phase-0f-grapple-ion-seam-ledger.json`) was reconciled: each of its five Grapple entries now carries an explicit `resolution` field (FIXED or NON-MATH WORKFLOW DEFERRED), so no document in this repository simultaneously claims a defect both unresolved and the domain fully certified. Full detail, including the complete fail-before matrix and all four new/extended test files, is in the Grapple domain section's "Certification-correction addendum 7".

**Wording standard, extended a final time**: "opposed-check-certified" requires every opposed Grapple check's tie-resolution rule to be proven through one shared decision function; "state-effect-certified" requires every grapple-state numeric defense effect to be traced to a published rule and proven component-aware where the rule itself is. Both are now true for Grapple. Per the required certification split: **GRAPPLE MATH: CERTIFIED. GRAPPLE STATE NUMERIC EFFECTS: CERTIFIED. ATTACK TARGET-DEFENSE AUTHORITY: CERTIFIED.** *(Corrected by round 8 below: this line was premature — the same states' own summary text still described a missing -2 attack-roll penalty, and the target-defense fix was a correctly-ordered duplicate of `SchemaAdapters.getDefenseTotal()`, not yet one shared function.)*

## Batch 1 certification correction, round 8 (post-review): the -2 Grabbed/Grappled attack-roll penalty was still missing, and the defense-authority fix was a correctly-ordered duplicate, not a true single authority

A ninth review accepted every round 7 fix but correctly refused the "GRAPPLE STATE NUMERIC EFFECTS: CERTIFIED" claim: round 7's own replacement summary text for Grabbed/Grappled still read "-2 on attack rolls except natural/light weapons," and nothing in the code computed it — a wrong player-visible attack modifier for most attacks made while Grabbed/Grappled, not a workflow nicety. Separately, round 7's `attacks.js` target-defense fix corrected the priority order but still inline-read `system.derived.defenses.<key>.total` itself, the exact same read `SchemaAdapters.getDefenseTotal()` already performs — correct by matching coincidence, not by delegation.

**Fixed**: `GrappleStateEngine.getAttackPenalty(actor, weapon)` computes the real -2 (or 0 when the attack is unarmed/natural/light, or the actor is Pinned rather than Grabbed/Grappled — Pinned's attacks are already blocked outright by Pin's own action legality, so a numeric penalty there would be meaningless double-gating), reusing this engine's own existing `classifyGrappledAttack()` classifier rather than a new heuristic (a repository-wide search found 5–6 independent, mostly narrow/unreferenced "is this light/natural" implementations scattered across the codebase and no single canonical one to delegate to instead — folded into the already-queued Batch 2 weapon-schema item as the same underlying gap). The penalty is a new, provenance-bearing entry in `attacks.js#rollAttack()`'s existing canonical attack contribution ledger (the same one Fighting Defensively already uses), so roll and chat-breakdown parity holds by construction. Separately, a new shared primitive, `SchemaAdapters.getDefenseTotalIfPrepared(actor, defense)`, returns the real derived value or `null` (never a default); `getDefenseTotal()` is now defined in terms of it, and `attacks.js`'s target-defense reads call the same primitive, so the two can no longer independently drift. Full detail, including the complete fail-before matrix and both new test files, is in the Grapple domain section's "Certification-correction addendum 8".

**Wording standard, corrected and finalized**: a numeric grapple-state effect is either fully implemented (both its defense-side and attack-side components, where the published rule has both) or it is not certified — a partial implementation with an accurate prose description of the missing half does not qualify. Target-defense authority additionally requires one shared function, not two independently-maintained reads that happen to agree. Both are now true: **GRAPPLE MATH: CERTIFIED. GRAPPLE STATE NUMERIC EFFECTS: CERTIFIED (defense-side AND attack-side). ATTACK TARGET-DEFENSE AUTHORITY: CERTIFIED (one shared function).**

- Consumers (B): `base-attack-bonus-rule.js:22`, `combat-roll-math.js:413,471,479` (both via `SchemaAdapters.getBAB`), `character-like-sheet.js:1473-1479` (read-only fallback chain, correctly prioritized `derived.bab` first, not a reimplementation).

This is a genuine two-box disagreement risk: `combat-stats-panel.hbs`'s BAB box (`buildCombatStatsPanel()`, already correctly `derived.bab`-only) and `resources-panel.hbs`'s BAB box could show different numbers for the same PC whenever a stale `system.baseAttackBonus` value existed (e.g. imported/legacy actor data). **Fixed**: priority flipped to `derived.bab ?? system.baseAttackBonus`, matching `character-like-sheet.js`'s already-correct pattern. `system.baseAttackBonus` remains a genuine, separate authority for NPCs/vehicles/droids/followers (a flat statblock field for actor types that don't run the class-based `BABCalculator` pipeline) — that usage is untouched; this fix is scoped to the PC sheet's resources-panel box only. current classes + current level + generic hit-die average → reconstruct entire HP history

### Defect A — CONFIRMED, live-executed: `ActorEngine.recomputeHP()`'s stateless-recompute model is incompatible with the real HP authority

The real, currently-correct HP authority is **`scripts/apps/progression-framework/shell/progression-finalizer.js`**, not `ActorEngine.recomputeHP()`:
- Chargen (`:1458-1466`): `system.hp.max` = a one-time computed starting HP.
- Level-up (`:1511-1534`): `nextHpMax = currentHpMax + hpGain`, where `hpGain` is **the player's actual chosen amount for that specific level** (`summary.hpGain`, sourced from whichever method — rolled/average/maximum — was used, recorded verbatim into `system.progression.hpGainHistory` and `lastHpGain`). This is **additive and history-preserving by construction**: each level's class and hit die are correctly used at the moment of that level's gain (confirmed against Gar'ee's own `classLevelHistory`/`hpGainHistory`: level 7 and 8 both show Soldier, hitDie 10, CON mod 2, method "maximum", amount 12, `previousMax: 96 → newMax: 108` — exactly matching `96 + 12 = 108`).

`ActorEngine.recomputeHP()` (`actor-engine.js:3781-3894`) is a **fundamentally different, stateless model**: it discards all of that history and recomputes `hpAtFirstLevel + (level-1)*hpPerLevel + conMod*level + bonusHP + featHPBonus` from scratch, using only the *current* first class item's hit die/progression fields and a flat per-level average (`floor(hitDie/2)+1`) for every level. This is wrong for **any** character with real per-level history, not only multiclass ones — a single-class character who rolled or chose maximum HP at any level would also have that choice silently discarded and replaced with the generic average the instant this function successfully writes.

For Gar'ee specifically (Soldier 6/Scoundrel 2, CON +2, level 8, first class = Soldier per above): `recomputeHP()`'s formula computes `30 + 7*6 + 2*8 = 88`. **Precision on what "88" is and isn't**: 88 is a formula/source-level derivation — the literal arithmetic quoted directly from `actor-engine.js:3844-3846`, hand-evaluated with Gar'ee's real inputs. It is **not** a value the live function has ever been observed to return or write: per Defect B, the function throws before reaching its `return newHPMax;` statement, so `newHPMax`'s runtime value was never captured, logged, or asserted equal to 88 in any test. What **is** live-verified (against the real, unmodified `ActorEngine.recomputeHP()`, imported directly to bypass this repo's own test-only fake — see Defect B below) is narrower and different in kind: that the function enters its value-changing branch (`newHPMax !== currentMax`) for Gar'ee's real data, and crashes there with a `ReferenceError` before writing anything. The 88 figure explains *why* that branch is entered (a real, computed difference) without itself being something execution confirmed. This would silently overwrite Gar'ee's correct, history-derived 108 with a value the formula computes to 88 **if it ever successfully ran and returned** — which, per Defect B, it currently cannot.

**Classification: CONFIRMED — `recomputeHP()`'s reconstruction model is the defect; Gar'ee's 108 is not.** Not merely a multiclass-formula gap, and not "Gar'ee currently has 88 HP" — his persisted, certified-correct value remains 108. The finding is precisely and only that this function would produce 88 from his current class/level/CON state if it ever successfully wrote, discarding his legitimate history. **If any function wants to turn Gar'ee into 88, that function is the defect — 108 is not.**

### Why this is not "just multiclass hit dice" — an authority contract is required before any fix

Per explicit project direction: **do not fix HP by looping through current class levels.** The real authority (`progression-finalizer.js`) is fundamentally **additive/incremental with locked-in historical per-level choices** (rolled, average, or maximum HP, decided once at the moment of that level-up and never revisited). `ActorEngine.recomputeHP()`'s model is **stateless/recompute-from-scratch with a generic per-level average**. These two models cannot be reconciled by "use the right hit die" alone — they disagree in kind, not just in formula. Fixing `recomputeHP()` to iterate real per-class hit dice (matching dead-code `HPCalculator.calculate()`'s already-correct multiclass accumulation) would still discard any level where the player rolled or chose maximum rather than average, silently replacing a real (possibly higher or lower) historical value with a generic one.

A closer read of `MetaResourceFeatResolver.getHitPointMaxBonus()` (`meta-resource-feat-resolver.js:155-170`) shows `featHPBonus` supports both a flat `MAX_BONUS` (e.g. Toughness) and a level-scaling `MAX_BONUS_PER_LEVEL` — genuinely recomputable bonus terms, independent of the locked-in per-level base. This suggests the real fix is architectural, not a formula swap: **separate the locked historical base HP (owned exclusively by `progression-finalizer.js`, append-only, never recomputed) from recomputable bonus deltas (CON-mod-driven `bonusHP`, feat-driven `featHPBonus`) that `recomputeHP()` could legitimately reapply on top of that base without ever reconstructing the base itself.** Today `system.hp.max` is a single merged field with no persisted separation between "locked base" and "last-applied bonus," so implementing this cleanly requires either persisting that separation explicitly or deriving it some other way — an actual design decision, not a one-line fix.

Note on item 3 above: SWSE RAW actually *does* say a Constitution modifier change retroactively rescales HP "as if you had that Constitution modifier since 1st level" — so `conMod * level` is not wrong in *kind*, only in combination with a base that (per `hpGainHistory`) already has the *old* CON mod baked into each historical `amount`. Correctly supporting RAW's retroactive-CON rule requires knowing the CON-*free* hit-die-only component of the historical base separately from the applied CON contribution — which isn't persisted separately today. This sharpens, rather than resolves, point 1 above: the required persisted-data shape must separate at least three things — locked hit-die-only history, the CON mod that history should currently be rescaled against, and other recomputable bonus deltas (feats, `hp.bonus`).

**Per explicit instruction: no HP code change in this pass.** Required before implementation (not yet done):
1. Decide the persisted-data shape that lets `recomputeHP()` (or its replacement) apply/reapply bonus deltas — including RAW's retroactive CON rescaling — without ever reconstructing the per-level-accumulated base.
2. Audit `progression.hpGainHistory`/`classLevelHistory` completeness for **legacy actors** who leveled up before these history fields existed (an actor with `system.hp.max` set but empty/partial `hpGainHistory` needs a defined fallback that doesn't equal "recompute from scratch and silently disagree").
3. Confirm the CON-retroactivity nuance above against this codebase's actual intended house rules (it may already deliberately deviate from RAW here — needs a decision, not an assumption either way).
4. Fix Defect B (the scope bug) — but **only together with, or after, Defect A**, never in isolation (see the warning at the end of `tests/hp-preservation-authority.test.mjs`): removing the crash alone would unmask Defect A's destructive overwrite for every actor with real per-level history, not just multiclass ones.

Guard comment confirms the intended single-writer *contract* is sound (`actor-engine.js:618`: "[HP SSOT Violation] system.hp.max may only be written by ActorEngine.recomputeHP()") — the problem is that `recomputeHP()` itself doesn't yet implement a model compatible with the real, additive authority `progression-finalizer.js` already correctly uses.

### Blocker 3 — NPC flat statblock composition was over-broad

### Blocker B — Charge/Flanking flattened into an anonymous, untyped `situationalBonus` number before reaching the final composition

Even after Blocker A's melee gate, Charge and Flanking were summed into a single anonymous `situationalBonus` number before `computeFinalAttackComposition()` ever saw them — losing source identity, modifier type, and stacking behavior, and collapsing into one unlabeled "Situational Bonus" ledger row instead of one row per source. This made a same-type collision (e.g. two Flanking-granting sources) mathematically unrepresentable, and made Powerful Charge's real "additional +2" (see below) indistinguishable in the ledger from Charge's own +2.

**Fix — a typed contribution seam, not attack-specific ad hoc logic:**
- `ModifierTypes.js` gained one new stacking category, `ModifierType.FLANKING` (`STACKING_RULES.flanking = 'highestOnly'`): a target is flanked or it isn't, from one geometric fact, so a second/third flanking-granting source must not let the bonus apply twice — `highestOnly` gives that semantics correctly using the project's existing stacking-rule vocabulary, without inventing a new rule.
- `computeAttackSituationalContext(form, melee)` now returns `situationalContributions: Modifier[]` (built via the project's own `createModifier()` factory) instead of a bare `situationalBonus` number: Charge is `{ source: CONDITION, sourceId: 'charge', sourceName: 'Charge', type: UNTYPED, value: 2 }` (melee-gated), Flanking is `{ source: CONDITION, sourceId: 'flanking', sourceName: 'Flanking', type: FLANKING, value: 2 }` (melee-gated, per Blocker A).
- `computeFinalAttackComposition()` (`attacks.js`) resolves `rollOptions.situationalContributions` through `ModifierUtils.getModifierDetail(contributions, 'global.attack')` — the project's existing pure typed-stacking authority (`ModifierUtils.resolveStacking()`, driven by `STACKING_RULES`) — rather than any new highest-only/collision logic written for this seam. Its resolved `.total` feeds `atkBonus`; its resolved `.applied` list (plus any suppressed contributions, with their suppression reason) is turned into one ledger row per contribution via the existing `buildModifierLedger()` helper (`modifier-breakdown-builder.js`) — so "Charge" and "Flanking" (and any future contextual contribution) each get their own named, provenance-carrying ledger row.
- A raw numeric `rollOptions.situationalBonus` (a legacy caller, or an explicit GM override) is still honored, added separately as `legacySituationalBonus`, and surfaced as its own "Situational Bonus (legacy)" ledger row distinct from the typed contributions — an explicit, clearly-labeled compatibility path, not the primary semantic source for Charge/Flanking.

**Disclosed deviation from the review's literal suggestion:** the review's phrasing suggested Charge could be represented as a `competence`-style bonus. Before implementing that, `packs/feats.db` was checked for real RAW evidence and Powerful Charge's actual benefit text reads: *"When you Charge, you gain an **additional** +2 bonus on your melee attack roll."* That word "additional" proves base Charge's +2 and Powerful Charge's +2 must **add**, not collide — a `highestOnly` type (competence or otherwise) would silently suppress Powerful Charge's real bonus, introducing a new defect while fixing this one. Charge is therefore typed `ModifierType.UNTYPED` (SWSE's default "always stacks" category), not `COMPETENCE`, so a future Powerful-Charge-as-typed-modifier contribution stacks correctly with it. This is called out explicitly rather than silently substituted, per this project's charter of proving each claim rather than guessing.

Required tests, all in `tests/attack-bonus-math-integrity.test.mjs`'s new typed-contribution block (Section 5): (1) Charge appears as its own named ledger row; (2) Flanking appears as its own named ledger row; (3) Charge+Flanking both apply to a legal melee attack and remain two separate ledger rows summing to +4; (4) ranged Flanking contributes zero, proven end to end through the real dialog/roll shared pipeline; (5) Charge's UNTYPED type correctly **stacks** (not collides) with a same-type Powerful-Charge-shaped contribution, matching the "additional +2" RAW text, plus a genuine same-type collision proof using two FLANKING-typed contributions (only the higher applies, via `ModifierUtils`, not ad hoc logic); (6) cross-type Charge(untyped)+Flanking(flanking-typed) always stack regardless of value, independent of same-type collision resolution; (7) `SUM(applied ledger contributions) === atkBonus` holds in every case above, including the collision case where one contribution was suppressed by stacking.

**Certification-correction addendum 5 (post-review, round 5): static and contextual modifiers were being composed in two separate stacking universes.** A sixth review found the one remaining defect in round 4's design: `_rollGrappleBonus()` combined the static total and the contextual total as two plain **numbers** —

```js
let bonus = staticGrappleTotal;       // already stacking-resolved, but now just a scalar
bonus += swseTalentGrappleBonus(actor, mode);  // also just a scalar
```

— which discards each side's bonus `type` before they ever meet. This codebase's own modifier-stacking rules (`ModifierUtils.STACKING_RULES`) say `competence: 'highestOnly'` — two competence bonuses from different sources should never both apply, only the higher. But because the static Enslaved competence bonus (+2) had already been collapsed into a bare number by the time Expert Grappler's contextual competence bonus (+2) was added, the actual live result was **+4** in an `attackGrapple` roll, not the RAW-correct **+2**. **Live-reproduced exactly as described**: an actor with both sources present rolled `core + 4` instead of `core + 2`. The bug is specific to same-type collisions — an actor with only one of the two sources, or with sources of two *different* stacking types, was already correct, which is why rounds 1–4's testing never caught it.

**Fixed**: contextual Grapple contributions (`GRAPPLE_BONUS` talent/feat rules, `RESIST_GRAB_AND_GRAPPLE`) are no longer pre-summed to a number before combining with the static side. `collectContextualGrappleModifiers()` (renamed from `swseTalentGrappleBonus()`, in `grappling-system.js`) now returns modifier **objects** (`{source, sourceId, sourceName, target:'grapple', type, value, enabled, description}`, built with the same `createModifier()` factory `ModifierEngine` uses) for every mode-applicable rule on the actor's items. `_rollGrappleBonus()` now:
1. Reads the core term (BAB + higher of STR/DEX + size + species — which never stacks against anything) directly from `system.derived.grappleBonusParts.core`, not the combined total.
2. Reads the actor's already-resolved static modifier objects from `system.derived.modifiers.breakdown.grapple.applied` (the same array `DerivedCalculator` used to build the canonical total — not re-derived).
3. Unions the static and contextual modifier arrays and runs them through `ModifierUtils.resolveStacking()` — the **same shared stacking authority** every other domain in this codebase uses — followed by `ModifierUtils.sumModifiers()`.
4. Returns `core + modifierTotal`.

Re-running `resolveStacking()` over the union of an already-resolved static set and a freshly-built contextual set is safe: the function groups strictly by `type` and re-derives each group's result from scratch, so it doesn't matter that the static half was already reduced to its own per-type winner(s) before contextual entries of the same or different types are added to the pool. No Grapple-specific stacking logic was hand-coded anywhere — the fix is entirely "collect real modifier objects, hand them to the existing authority."

`Grapple Resistance`'s `RESIST_GRAB_AND_GRAPPLE` rule carries no explicit `bonusType` in its authored data, so it's treated as `untyped` (the same default this codebase applies everywhere else a bonus's type isn't stated) — `untyped` stacks with everything, matching its RAW behavior as an unlabeled feat bonus. `MetaResourceFeatResolver.getGrappleResistanceBonus()` itself was left untouched (it has one other, unrelated caller for a Reflex Defense bonus at grab-attempt time); `_rollGrappleBonus()` now derives its own `RESIST_GRAB_AND_GRAPPLE` modifier objects directly from the same `abilityMeta.grappleRules` data instead of calling that number-returning helper for the Grapple-check use case specifically.

**Live-verified invariant, round 5** (`tests/grapple-static-modifier-composition.test.mjs`, rewritten): a full stacking-collision matrix — equal competence values (+2 vs +2 → +2, not +4, the exact round-4 regression), a higher contextual value replacing a lower static one (+4 beats +2), a lower contextual value failing to replace a higher static one (+2 beats +1), and a different-typed contextual bonus (`circumstance`) correctly composing additively alongside the static competence bonus rather than being capped by it. Every prior invariant (SSOT, book values, static-modifier composition, mode gating) is re-verified unaffected.

**Wording standard, extended again**: "stacking-certified" is claimed only once every contextual Grapple contribution is proven to be resolved against the actor's static contributions through the same shared stacking authority as everything else in the codebase — not merely added as a number on top of an already-collapsed total — across same-type collisions in both directions and at least one cross-type case. That is now true for Grapple.

**1. The `RESIST_GRAB_AND_GRAPPLE` rule type was overloaded to mean two different SWSE mechanics with one field.** Its real compendium text for two different feats:
- **Grapple Resistance**: "+5 Reflex Defense against Grab/Grapple attacks AND +5 to all opposed Grapple checks" — both channels, coincidentally the same value.
- **Grab Back**: "+2 Reflex Defense against Grab and Grapple attacks. If the enemy misses, [a reaction] counter-grab." — **the Reflex channel only, no opposed-check bonus at all.**

Both were authored with the identical single-field shape (`{type:'RESIST_GRAB_AND_GRAPPLE', bonus:N}`), so round 5's `collectContextualGrappleModifiers()` — which reads this type for the *opposed-check* channel — incorrectly credited a Grab Back defender with +2 on their own opposed Grapple checks, a bonus that feat does not grant. This was invisible through round 5 only because Grapple Resistance's two channels happen to share a value.

**Fixed** by splitting the channels explicitly in the rule shape itself — `GRAB_GRAPPLE_RESISTANCE: {reflexBonus, opposedGrappleBonus, source}` — rather than special-casing either feat's name anywhere in consuming code. Every live producer of this metadata was migrated, all three found by repository-wide search, not assumed to be singular:
- `packs/feats.db` / `packs/feat-catalog.db` (the shipped compendium NDJSON records themselves).
- `data/feat-catalog.json` — a separate, independently-loaded live JSON array (confirmed consumed by `feat-registry.js`, `feat-pack-seeder.js`, `feature-index.js`, `compendium-pack-registration-repair.js`), carrying its own copies of the same two records.
- Two independent normalization hooks that can also *produce* this metadata at runtime: `grapple-feat-normalization-hooks.js#rulesForFeat()` (fires on item create/update) and a second, separate hook in `hp-recompute-hooks.js#HPRecomputeHooks.featureRuleNormalizationPatch()` (guarded by a non-source-specific `hasExistingGrappleRules()` check, confirmed dormant in practice for these two feats since the compendium already ships non-empty `grappleRules` — fixed anyway for consistency, in case it ever fires against a bare/legacy item).

Both consumers now read the correct channel: `MetaResourceFeatResolver.getGrappleResistanceBonus()` reads `reflexBonus` (its one live caller is `attemptGrab()`'s Reflex-Defense-vs-incoming-Grab check); `collectContextualGrappleModifiers()` reads `opposedGrappleBonus` (the wielder's own opposed-check roll). ```

`system.defenses.reflex` is a field the V2 character pipeline never populates (`DerivedCalculator` writes only to `system.derived.defenses.reflex`) — so for an ordinary V2 PC, this silently collapsed to the hardcoded fallback of `10`, regardless of the character's real Reflex Defense. **Fixed**: `attemptGrab()` no longer recomputes hit/miss at all. ## Domain: Weapon Melee/Ranged Schema — CONFIRMED DEFECT (the "Bluebolt" bug)

**Verdict: the reported mechanism is real, and directly confirmed on a real, currently-played actor.** While not present in any shipped compendium/pack data (364 standalone weapon items + ~1989 actor-embedded weapons across all packs checked — zero mismatches there), Gar'ee's own actor export contains the exact contradiction: his "Bluebolt Blaster Pistol" item has `weaponCategory:"ranged"`, `category:"pistol"`, `proficiency:"pistols"`, `attackAttribute:"dex"` (all correctly ranged) alongside `meleeOrRanged:"melee"` and `ranged:false` (both wrong). This is not a theoretical authoring hazard — it is live, manifested data on a real character, reachable through completely normal sheet use (not just direct DB editing).

**Root cause:** `template.json` defines 5 independent, schema-unlinked fields: `weaponCategory`, `proficiency`, `attackAttribute`, `meleeOrRanged`, `ranged` (legacy boolean). The item sheet's branch-change handler (`scripts/items/swse-item-sheet.js#onMeleeOrRangedChange`, :2351-2365) only (a) sets a client preview flag, (b) repopulates the `weaponCategory` dropdown with `preserveValue:true` — meaning a category string valid in both melee and ranged lists (e.g. `simple`) silently survives a branch flip without actually changing, and (c) re-hydrates range-band fields. It **never touches `system.ranged` or `system.proficiency`, and never re-derives `system.attackAttribute`.** The one branch-aware save-time reconciliation block (`#onSubmitForm`, :2661-2679) only syncs range-band fields, conspicuously omitting `ranged`/`proficiency` — confirming the omission is structural, not incidental. `normalizeItemSystem` (`item-defaults.js`) never reads or writes either field (grep-confirmed zero occurrences).

**Net effect (directly matches the reported bug):** a weapon created as melee, then switched to Branch=Ranged/Category=Pistols via the sheet, saves with `meleeOrRanged:"ranged"` and correct pistol range bands, but `ranged` stays `false`, `proficiency` stays `"simple"` (not `"pistols"`), and `attackAttribute` stays whatever it was — exactly the Bluebolt contradiction.

**No single canonical field is enforced.** `meleeOrRanged` is the de facto primary for most modern consumers (`combat-stat-rules.js`, `roll-config.js`, `weapon-range-profile-resolver.js`, `combat-ui-behavior-hotfix.js`, droid sheet) — but a real minority of consumers **ignore it entirely**, pattern-matching on other fields instead:
- `scripts/engine/species/rage-engine.js:79-100` — text search over `system.combat.range` (a **dead field that doesn't exist** in template.json), `system.range`, `weaponType`, `weaponGroup`, `system.category` (not `weaponCategory` — wrong field name).
- `scripts/engine/talent/sith-talent-actions.js:242-249` — same wrong-field text-search pattern.
- `scripts/apps/force-alchemy/force-alchemy-context-resolver.js:209-215` — category/name regex, ignores `meleeOrRanged`.
- `scripts/combat/utils/combat-utils.js:119-123` local `isMeleeWeapon` — checks `system.range` string equality, ignores `meleeOrRanged`.
- `scripts/engine/combat/weapons-engine.js:51-53` `isMeleeWeapon` — checks `weapon.system.combat.range.type`, a field that **does not exist anywhere in the schema** — this predicate is always `false`; dead/vestigial, no other callers found.
- `scripts/engine/inventory/ammo-system.js:450-452` — `meleeOrRanged==='ranged'` **OR** `range !== 'Melee'` (OR, not fallback) — actively diverges from `meleeOrRanged` if `range` text isn't literally `"Melee"`.
- `scripts/engine/combat/damage-type-rules.js:217-218` — falls through to `system.category` (wrong field name, doesn't exist) before `options.attackType`.
- `scripts/items/weapon-data-resolver.js:87-120` (`normalizeBranch`) — `meleeOrRanged==="ranged"` always wins, but `meleeOrRanged==="melee"` can be **silently overridden to ranged** by category/name text heuristics — a second, one-directional inconsistency-repair mechanism layered on top of the first bug.

**Classification: CONFIRMED**, with a clear recommended remediation already identified by the audit (not yet implemented): make `meleeOrRanged` the single enforced SSOT field, add a normalization step in `normalizeItemSystem` that derives/resets `ranged`/`proficiency`/`attackAttribute` whenever `meleeOrRanged` changes, and repoint the ignoring consumers onto `combat-stat-rules.js`'s canonical `isMeleeWeapon`/`isRangedWeapon` helpers.

**Related finding, folded in from the Grapple domain's round 8 (same underlying gap, not a new one):** "is this a light weapon" / "is this a natural weapon" classification has the identical no-single-SSOT-field problem as melee/ranged above, and touches several of the exact same files. At least 5–6 independent implementations exist: `combat-utils.js#isLightWeapon(weapon, actor)` (wielder-size-relative — the mechanically correct SWSE rule — but referenced by nothing else in the codebase), `weapons-engine.js#isLightWeapon()` (checks a `traits` array for the literal string `'light'`, despite its file's own "V2, structured schema, canonical" header comment — grep-confirmed zero weapons in this repository's actual compendium data carry that trait, so this predicate is effectively always `false`), plus separate local `isLightWeapon`/`isNaturalWeapon` heuristics in `dual-wield-combat-shape-resolver.js`, `core-attack-option-runtime-patches.js`, `CombatEngine.js`, and `reaction-registry.js`. `grapple-state-engine.js#classifyGrappledAttack()`'s own text/trait-based classifier (used both for Grapple's attack-legality gate and, as of round 8, its `-2` attack-penalty exemption) is a further, Grapple-domain-scoped implementation. None of these was touched, unified, or torn down this round — recommended remediation is the same in kind as melee/ranged: pick one canonical light/natural-weapon predicate (ideally schema-driven, matching real compendium data rather than an always-false trait check) and repoint every consumer, including Grapple's own classifier, onto it.

**Shipped-data blast radius, confirmed by full scan of all `packs/weapons*.db` files:** of every ranged-categorized weapon record (`weaponCategory` containing "ranged"/"pistol"/"rifle"/"heavy"/"exotic-ranged"), **302 records omit `meleeOrRanged` entirely, and zero conflict with an explicit wrong value** — meaning Bluebolt is not a special case. **Real-data schema discovery that reorders the fix's precedence:** a full scan of all weapon pack records (744 total) shows `system.weaponCategory` holds a literal `"melee"`/`"ranged"` branch value on **100% of shipped records, with no exceptions** (604 ranged, 140 melee) — it is empirically the true, always-authored branch field in this codebase's real data, not `meleeOrRanged` (absent on all 744). ### Phase 2 — SWSE rule contract (verified against this repository's own existing rules-fidelity audits, `docs/audits/combat-phase-0a-rules-source-baseline.md`)

- **Melee attack roll:** `1d20 + BAB + Strength modifier`. **Ranged attack roll:** `1d20 + BAB + Dexterity modifier + range penalty`. A weapon's BASE branch (melee/ranged) is a persistent identity of the weapon; the ability used on a given attack is a separate, configurable field (`system.attackAttribute`) that defaults from branch but is not redefined by it (see the Attack-Ability Policy below).
- **Thrown attacks:** SWSE explicitly allows a melee weapon (typically a Light Weapon, e.g. a vibrodagger or a thermal detonator-like thrown weapon) to be thrown as a ranged attack (uses Dex, subject to range penalties) without converting the weapon's own persistent identity to "ranged." This is confirmed by this repository's own Phase 0A audit language distinguishing "melee/thrown melee damage" from "ranged damage" as two different DAMAGE contexts of potentially the same weapon. **Base weapon identity and attack-context classification are therefore two different concepts and must not be collapsed into one persisted field** — a thrown attack changes only the attack-context resolution (already the `attackType`/`context.attackType` inputs several consumers above already accept), never `system.meleeOrRanged`/`weaponCategory` on the item itself.
- **Light Weapon:** a weapon is a Light Weapon for a given wielder when the weapon's size category is smaller than the wielder's own size category (`combat-utils.js#isLightWeapon(weapon, actor)`'s size-relative logic is confirmed, by direct comparison against the SWSE Core Rulebook's size-and-weapon rules, to be the correct implementation of this rule — not a generic d20 "Light" weapon-type tag). This is wielder-relative, not a fixed weapon property, confirming why the predicate must take `actor` as an input and cannot be a pure item-only classification.
- **Natural/unarmed weapon:** an attack made with a body part (claws, bite, horns, etc., typically species-granted) or an unarmed strike. Relevant here specifically because it is one of the two exemption categories (alongside Light Weapon) from the Grabbed/Grappled `-2` attack-roll penalty (`data:` "Grabbed target cannot move and takes -2 to attacks unless using a Natural Weapon or Light Weapon" — Phase 0A baseline, confirmed unchanged by this audit).
- **Attack ability is not branch-derived beyond an initial default.** SWSE has numerous feats/talents/species abilities/weapon traits (Weapon Finesse-style DEX-for-melee substitutions, STR-for-thrown-heavy weapons, etc.) that legitimately change which ability a given weapon uses. The engine does not currently have complete rules coverage to infer all of these safely, so `system.attackAttribute` is player/data-owned configuration once set — the schema authority may supply a sensible default (ranged → dex, melee → str) only when the field is absent, and must never treat `attackAttribute` as evidence of branch (an explicit `melee` weapon with `attackAttribute: "dex"`, or an explicit `ranged` weapon with `attackAttribute: "str"`, are both legal, non-contradictory states).

### Phase 4 — implementation architecture (canonical authority)

New module: `scripts/items/weapon-branch-resolver.js`. Exports:

- **`resolveWeaponBranchFamily(itemOrSystem)`** — the canonical branch/family/coherence resolver. Precedence (reordered from every existing consumer, per the real-data discovery above): (1) `weaponCategory` literal `'melee'`/`'ranged'` value, when present — the only field empirically populated on 100% of real records; (2) `proficiency`/`subcategory`/`category`/`weaponGroup`/`group` membership in an unambiguous melee-family set (`advanced`, `lightsaber`, `natural`, `melee-exotic`, `advanced-melee`) or ranged-family set (`heavy`, `heavy-weapons`, `pistols`, `rifles`, `ranged-exotic`) — `simple` and bare `exotic` are branch-ambiguous and never used alone to decide branch; (3) explicit `meleeOrRanged`/`weaponRangeType`/`rangeType`, consulted only when 1–2 are silent (demoted from every current consumer's top priority, since it is proven structurally untrustworthy — always absent in shipped data, always schema-defaulted on materialization); (4) range-profile/name-text heuristics; (5) default `'melee'`. Returns `{branch, family, proficiencyFamily, coherent, issues[]}` — `coherent:false` when the resolved branch and an unambiguous family/proficiency value disagree (the schema-coherence invariant: base branch, weapon family, proficiency family, subcategory, and range-profile/weapon-type must never persist a contradictory combination — melee+pistols, melee+heavy-weapons, ranged+lightsaber, ranged+natural, etc., are all invalid states, not just misreads).
- **`isRangedWeapon(item)` / `isMeleeWeapon(item)`** — the canonical branch predicates every consumer above delegates to.
- **`isLightWeaponForActor(weapon, actor)`** — promoted verbatim (size-relative logic) from `combat-utils.js`, now exported as the canonical authority; `combat-utils.js` re-exports it under its existing name instead of keeping its own incorrect local shadow.
- **`isNaturalOrUnarmedWeapon(item)`** — consolidates the ~4 near-duplicate implementations (structured flags/fields first, text pattern fallback).
- **`defaultAttackAttributeForBranch(branch)`** — `'dex'` for ranged, `'str'` for melee. Used **only** by the write-time normalizer below when `attackAttribute` is absent at creation; never consulted by `resolveWeaponBranchFamily()` or any branch/family classification (attack ability is never evidence of branch, and branch/family coherence never requires `attackAttribute` to match the branch default).
- **`normalizeWeaponBranchFamily(system)`** — the write-time coherence enforcer, invoked from a new `preCreateItem`/`preUpdateItem` hook scoped to `type==='weapon'` (mirroring this codebase's existing per-feat `preCreateItem`/`createItem` normalization-hook pattern) and from `item-defaults.js`'s `normalizeItemSystem()`. Given a candidate system object: resolves the coherent branch/family via `resolveWeaponBranchFamily()`, then corrects **only** the low-trust, schema-defaultable fields (`meleeOrRanged`, the legacy `ranged` boolean) to agree with the resolved branch — it never rewrites `weaponCategory`/`proficiency`/`subcategory` (the high-trust, deliberately-authored fields that are the actual evidence), and it never touches `attackAttribute` except to fill it from `defaultAttackAttributeForBranch()` when the field is entirely absent, preserving any explicit player-set value verbatim (including a value that intentionally differs from the branch default) and never overwriting it on an unrelated field edit. This stops the contradiction from being created on any future purchase/drop/creation, and self-heals it (in memory, non-destructively) on the next legitimate edit of an already-corrupted item — without requiring a data migration, since every read-time consumer above is being repointed onto `resolveWeaponBranchFamily()` directly and therefore never depends on the persisted field being correct in the first place.

### Batch 2B correction #2: `system.weaponCategory` was overloaded with two incompatible meanings (branch vs. family) — the real architectural blocker

A third independent review, checking commit `6f348f72a78435bd1ad556933c354930071ac7ea` directly, accepted both prior fixes (Attack-Ability Policy's six abilities; the honest Base-vs-Effective lightness non-certification) but found a deeper, previously-unnoticed architecture defect: **`system.weaponCategory` had been carrying two incompatible meanings simultaneously.** Shipped pack data authors it as the literal BASE BRANCH (`"melee"`/`"ranged"`) on 100% of records — the very fact `resolveWeaponBranchFamily()`'s tier-1 precedence relies on. But the V2 item editor's own Category `<select name="system.weaponCategory">` (`templates/dialogs/entity/parts/header.hbs`) had been writing FAMILY values into that exact same field the whole time (`advanced`/`lightsaber`/`melee-exotic`/`natural`/`simple` for melee; `heavy`/`pistols`/`ranged-exotic`/`rifles`/`simple` for ranged) — values that are never a literal `"melee"`/`"ranged"` string.

**Confirmed mechanism, reproduced exactly.** Because an editor-submitted family value never matches tier 1, `resolveWeaponBranchFamily()` fell through to tier-2 family evidence — read from `proficiency`/`subcategory`/`category`, none of which were live editor form fields (no `<input name="system.proficiency">`/etc. existed anywhere in the template) and were therefore silently carried over UNCHANGED from the item's prior, pre-edit state on every real form submission. On an explicit Branch change (e.g. Ranged → Melee), `swse-item-sheet.js#onMeleeOrRangedChange()`'s own `#populateWeaponCategoryOptions()` rebuilds the Category select's option list for the new branch and, when the previously-selected value has no match in the new list (the common case — a ranged family like `"pistols"` never appears among the melee options), silently defaults to the new list's first option (`"advanced"` for melee) — which then gets submitted as `weaponCategory`. The old, single-blob `normalizeWeaponBranchFamily(merged)` (both the item-sheet's `normalizeItemSystem()` call and the `weapon-branch-coherence-hotfix.js` preUpdateItem hook independently had this same shape) had no way to tell "the player just explicitly changed the Branch selector" apart from "the family fields are merely stale carryover" once current+submitted state had already been flattened into one object — so the just-submitted `meleeOrRanged:"melee"` was silently outvoted and reverted back to `"ranged"` by the stale, untouched `proficiency:"pistols"`. Reproduced exactly in `tests/weapon-branch-family-schema-authority.test.mjs` section 15 before any fix (confirmed to fail with the pre-fix code), matching the reviewer's description precisely.

A second, related symptom: opening a real, never-edited pack-shipped ranged weapon (`weaponCategory:"ranged"` literal) put that value into a Category `<select>` whose options for the ranged branch are `heavy`/`pistols`/`ranged-exotic`/`rifles`/`simple` — none of which is literally `"ranged"` — so the browser's own `<select>` element defaulted to its first option with no `selected` match, meaning even a completely unrelated field edit (e.g. renaming the item) could silently reclassify a real Bluebolt-shaped weapon's family from Pistols to Heavy on save.

**Field contract established (chosen to require zero pack-data migration, preserving the convention already authored in all 5,959 shipped weapon-type records):**

| Field | Canonical meaning going forward | Who writes it |
|---|---|---|
| `system.meleeOrRanged` | Canonical, player-facing BASE BRANCH (`"melee"`/`"ranged"`) | The editor's Branch `<select>`; every consumer should ultimately trust this field |
| `system.weaponCategory` | LEGACY/COMPATIBILITY MIRROR of the branch only, matching every shipped pack record's existing convention | No longer independently editable in the V2 editor; always kept in sync with the resolved branch at write time (`normalizeWeaponForWrite()`) |
| `system.subcategory` | Canonical, player-facing WEAPON FAMILY | The editor's Category `<select>` is now bound here (repointed from `weaponCategory`), using the real shipped singular vocabulary (`pistol`, `rifle`, `heavy`, `exotic`, `advanced`, `lightsaber`, `natural`, `simple`, `grenade`) confirmed by a direct scan of `packs/weapons*.db` |
| `system.category` | Pure alias, always mirrored from `subcategory` | Write-time normalizer only |
| `system.proficiency` | Pure alias, DERIVED from `subcategory` via a mapping table matching the real shipped proficiency vocabulary (confirmed by pack scan: melee = `exotic`/`advanced-melee`/`simple`/`natural`; ranged = `exotic`/`simple`/`heavy-weapons`/`pistols`/`rifles`) | Write-time normalizer only, whenever `subcategory` is explicitly set |
| `system.weaponGroup` / `system.group` | Untouched, read-time-only evidence | Never written by the normalizer |

`resolveWeaponBranchFamily()` (read-time, tolerant) is unchanged — a literal `weaponCategory:"melee"/"ranged"` remains its tier-1 signal, correct both for un-migrated legacy pack data (where it always holds branch) and for anything saved through the fixed write boundary (where it is now guaranteed to always hold branch, never family).

**Implementation.** A new function, `normalizeWeaponForWrite(currentSystem, submittedSystem, target)` (`scripts/items/weapon-branch-resolver.js`), receives the item's prior persisted state and the update's actual submitted keys SEPARATELY — never a pre-merged blob — so it can tell deliberate intent apart from stale carryover. Precedence: a literal `weaponCategory:"melee"/"ranged"` explicitly submitted wins first (matching `resolveWeaponBranchFamily()`'s own tier-1 authority and keeping single-object materialization/self-heal calls correct, since real pack-shaped data has both fields simultaneously "present" but only `weaponCategory` is trustworthy there); otherwise an explicitly submitted `meleeOrRanged` wins (the real, fixed editor's only live branch signal, since it no longer submits `weaponCategory` at all). ### Batch 2B correction #3: `template.json` itself still violated the new contract, and `preCreateItem` could not distinguish a template-fabricated default from genuine authored intent

A fourth independent review, checking commit `a8f42e85740d339444ac8ad2def5fb4f2af1b31a` directly, accepted the branch/family editor separation and the current-vs-submitted write provenance from correction #2, and confirmed CI green — but found two remaining data-boundary defects, both confirmed valid by direct inspection before any fix was made.

**Blocker 2 — `preCreateItem` could not distinguish a template-fabricated default from genuine authored intent.** By the time Foundry's `preCreateItem` hook fires, `document` has already been constructed by merging the raw creation payload (`data`) onto `template.json`'s schema — so `document.system` contains `attackAttribute: "str"` for ANY creation whose raw payload never authored that field at all, purely because the DataModel had to fill something in. `weapon-branch-coherence-hotfix.js`'s `correctedFields()` (as fixed in correction #2) treated `document.system` as genuine "current" state for both `preCreateItem` and `preUpdateItem` alike — correct for `preUpdateItem` (a real prior save genuinely exists there) but wrong for `preCreateItem` (there is no genuine prior state for a brand-new document; `document.system`'s un-authored fields are Foundry's own fabrication, not player input). ## Domain: Weapon Modifier Source Contract — CONFIRMED DEFECT — **FIXED**

Found live, as a side effect of building a real actor golden-case fixture (Vexa'na Fen'Orr'kess Tessik) to verify the certified Grapple formula against a second, independently-shaped character. Running her real actor export through `DerivedCalculator.computeAll()` threw a caught-but-logged error from `WeaponsEngine.getWeaponModifiers()`: `createModifier: missing required fields: source=undefined, sourceName=Lightsaber (Attuned)...`. Initially misdiagnosed as a data-quality issue on that one item; a follow-up review correctly identified it as a code defect.

**Root cause, confirmed directly against the source**: three `createModifier()` call sites in `weapons-engine.js` — the attuned-lightsaber +1 attack bonus, and both modifier builders in `#gatherLightsaberUpgradeModifiers()` (the standard-modifiers-array path and the direct damage-bonus path) — passed `source: ModifierSource.WEAPON`. `ModifierTypes.js`'s canonical `ModifierSource` enum has no `WEAPON` member (`FEAT, TALENT, SPECIES, BACKGROUND, ENCUMBRANCE, CONDITION, ITEM, EFFECT, DROID_MOD, VEHICLE_MOD, CUSTOM`), so `ModifierSource.WEAPON` always evaluated to `undefined` — which `createModifier()`'s own required-field validation correctly rejected. This is not malformed actor/item data: every other weapon-sourced modifier in this same file (enhancement bonuses, proficiency penalty, two-handed bonus, keen/flaming traits) already uses `ModifierSource.ITEM` — a weapon, and a lightsaber upgrade, are both ordinary Foundry Items — so the three `WEAPON` sites were simply inconsistent with the file's own established convention, never a second, deliberately-different category.

**A second, independent defect compounded this**: `getWeaponModifiers()` wrapped its entire multi-weapon `for` loop in one `try/catch`. A single malformed modifier from any one weapon (any weapon after the first, or the first weapon's own later checks) therefore threw out of the whole loop, silently discarding every other equipped weapon's modifiers collected in the same pass — not just the offending contribution. Live-reproduced: two equipped weapons, the first carrying a malformed lightsaber-upgrade modifier, the second an ordinary valid enhancement bonus — before the fix, the second weapon's modifier was never even attempted, since the loop aborted on the first weapon's throw.

**Fixed**: all three `ModifierSource.WEAPON` sites corrected to `ModifierSource.ITEM`, matching the file's existing convention (repository-wide search confirms these were the only three occurrences of `ModifierSource.WEAPON` in the codebase). Every `createModifier()` call in `getWeaponModifiers()`/`#gatherLightsaberUpgradeModifiers()` is now routed through a new `#pushModifierSafe(modifiers, data)` helper that catches and logs a single malformed contribution in isolation, so it can never affect any other modifier — from the same weapon or a different one — rather than relying on the outer, loop-wide `try/catch` as the only safety net.

**Live-verified**: Vexa's real actor export no longer produces the error when run through the real `DerivedCalculator.computeAll()` pipeline; her attuned lightsaber's +1 bonus is now correctly collected. `tests/weapons-engine-modifier-source-authority.test.mjs` proves, against the real `WeaponsEngine.getWeaponModifiers()` (not a reimplementation): an ordinary weapon, an attuned lightsaber (the specific fixed defect), a lightsaber upgrade with a standard-modifiers-array contribution, an attuned lightsaber plus upgrade together, and the required multi-weapon isolation case — a first weapon with a genuinely malformed upgrade modifier (a non-numeric `value`, not the already-fixed `WEAPON` bug specifically) must not erase a second, unrelated weapon's valid modifier. Every emitted modifier across every case is asserted against the full required shape: a canonical `source`, plus `sourceId`, `sourceName`, `target`, a canonical `type`, and a finite numeric `value`.

**Classification: CONFIRMED and FIXED.** Kept separate from the Weapon Melee/Ranged Schema domain above (a different kind of defect — a missing single-SSOT-field for branch/category consistency, not a modifier-construction contract violation) and from any other actor-specific audit findings from the same Vexa review — this entry is specifically the `ModifierSource.WEAPON` contract defect and its blast-radius fix.

### Batch 2A — implementation (fixes A1, A2, A4; supersedes the "3 overlapping implementations" framing)

While reproducing A1 before fixing it, the generic body-armor ACP formula was found to be independently wrong on its own terms, not just missing the shield case: `ModifierEngine._getItemModifiers()` computed `acp = armor.armorCheckPenalty; if (!proficient) acp += categoryPenalty;` — for Light armor (own listed ACP -2, category default also -2) this gave proficient → **-2** (wrong; SWSE RAW: proficiency suppresses ordinary armor's ACP to 0) and nonproficient → **-4** (wrong; double-counted the armor's own listed penalty against the category default; expected -2). The corrected rule, fixed together with the Energy Shield exception so the shield fix wasn't built on the wrong armor formula:

```
ordinary body armor: effectiveACP = proficient ? 0 : (item's own listed ACP, or the light/medium/heavy
                                                        category default only when the item has none)
Energy Shield, active: effectiveACP = the item's own listed ACP (or category default), ALWAYS, proficient or not
Energy Shield, inactive: no ACP, no Max Dex restriction, no Reflex penalty, no speed penalty, at all
```

### Batch 2A correction #2 — the equip-state fix had its own ordering bug; a single equip-state authority replaces it

A third review of Batch 2A accepted the shadow-DefenseCalculator removal and every other correction, but found one remaining architectural ordering bug: the first correction fixed the hotfix's equip-state normalization (`normalizeArmorEquipState()`) by moving it to run just before `DefenseCalculator.calculate()` — but `DerivedCalculator.computeAll()` runs `ModifierEngine.getAllModifiers()`/`aggregateAll()` (which drive ACP/skill modifiers via `armor-usage-resolver.js`) **before** it calls `DefenseCalculator.calculate()`. Confirmed by direct code reading (`derived-calculator.js` lines ~231-263): on the actor's first derived pass, a legacy-equipped item (`system.isEquipped`/`system.readied`/`system.equippable.equipped`/`flags.swse.equipped` instead of `system.equipped`) would be invisible to ModifierEngine — ACP/skill contributions silently omitted — even though Defense math, computed after the hotfix's mutation ran, came out correct. `system.derived.skills` and derived Initiative could be wrong for that one pass, "mysteriously" self-correcting on a later recomputation purely because the mutation had already happened by then — exactly the order-dependent behavior this freeze exists to eliminate.

A smaller, related defect in `ModifierEngine.getActorModifierSourceSignature()`'s cache-invalidation signature was also confirmed: `item?.system?.equipped ?? item?.system?.isEquipped ?? ''` uses `??`, which only skips `null`/`undefined` — so `system.equipped: false, system.isEquipped: true` hashed identically to `system.equipped: false` alone, silently losing the `isEquipped` signal from the cache key.

**Fix:** rather than relocating the mutation again, established one true equip-state authority. `isArmorItemEquipped(item)` (new export, `scripts/items/armor-data-resolver.js`) is now the single canonical "is this armor/shield item equipped" check — implementing the same broad legacy-shape recognition the hotfix used to apply via a mutation, but as a pure, read-time predicate every consumer calls directly instead:

- `armor-usage-resolver.js` — both `resolveBodyArmorContribution()`'s and the shield filter's equip checks.
- `ModifierEngine._getItemModifiers()`'s `equippedArmor` lookup.
- `defense-calculator.js`'s own `equippedArmor` lookup.
- `armor-benefit-simulator.js`'s `equippedBodyArmor()` (advisory consumer, fixed for full consistency).
- `armor-hydration-defense-hotfix.js`'s `isWornArmor()`/`findEquippedWornArmor()` (used only by its two UI panel patches — `buildArmorSummaryPanel`/`buildInventoryPanel` — a display concern unrelated to defense/skill math) now delegate to the same shared check instead of maintaining a fourth duplicate copy of the same logic.

No consumer depends on any other subsystem having run first, and no mutation of shared actor/item state happens anywhere. **`armor-hydration-defense-hotfix.js`'s `normalizeArmorEquipState()` and `installDefenseCalculatorPatch()` are removed entirely** — DefenseCalculator now recognizes a legacy equip-flag shape on its own, with zero help from any hotfix, so the hotfix no longer touches `DefenseCalculator.calculate()` in any way. Its only remaining responsibilities are the two UI panel patches and the unrelated Effect Builder partial registration.

The modifier-source signature bug is fixed by giving each legacy equip-flag field its own slot in the signature array (`system.equipped`, `system.isEquipped`, `system.readied`, `system.equippable.equipped`, `flags.swse.equipped`, each independently), rather than collapsing two of them through a lossy `??`.

**Verified:** `tests/legacy-equip-state-single-pass-authority.test.mjs` — a single `DerivedCalculator.computeAll()` pass on a Gar'ee-shaped actor whose shield and body armor are BOTH equipped via legacy/alternate flag shapes (including the specific adversarial case `system.equipped: false` / `system.isEquipped: true` for the shield, and `system.equippable.equipped: true` with no `system.equipped` at all for the armor) produces the correct ACP-affected skill totals, correct derived Initiative (with the `system.derived.skills.initiative.total === system.derived.initiative.total` parity check), correct defenses, and correct roll-dialog totals (`getSkillTotal()`/`buildRollConfigModel()`) — all on that first pass, no second recomputation needed. `tests/armor-hydration-hotfix-shadow-authority-removal.test.mjs` was updated to match: it now proves the hotfix's registration has zero effect on `DefenseCalculator`'s output (trivially true now that the hotfix never touches it) and that `DefenseCalculator` recognizes a legacy equip-flag shape with no mutation of the item at all.

ENERGY SHIELD REFLEX/MAX-DEX: CERTIFIED. ENERGY SHIELD SPEED: CERTIFIED. GAR'EE ACTIVE/INACTIVE SKILL PARITY: CERTIFIED. EQUIP-STATE DETECTION: CERTIFIED (single authority, order-independent).**

## Cross-cutting theme across every domain audited

The codebase already has the *right pattern* in exactly one place — `DerivedCalculator`'s skill contribution ledger, which sums named parts, compares the sum against the stored total, and logs a warning on mismatch (`derived-calculator.js:680-733`). **No other domain has this self-checking pattern yet.** The freeze's Phase 13 contribution-ledger contract should generalize this exact mechanism (already proven, already shipping) to BAB, defenses, damage threshold, HP, attack, damage, and grapple, rather than inventing a new architecture.

The single largest, most consistent finding across all 6 audits: **duplicate fallback formulas are pervasive (at least 25+ distinct reimplementation sites found across skills/initiative/defenses/BAB/grapple/attack/condition-track), but the large majority are guarded (only fire when canonical derived data is unavailable) and currently numerically consistent.** The genuinely load-bearing, CONFIRMED-wrong-today defects are a much shorter list — see the First Report below.

This is the value the source arithmetic algebraically produces for Gar'ee's real inputs — it is **not** a value the live function was observed to return. In practice, on Gar'ee's real data, the calling hooks swallow the thrown error — so `system.hp.max` is never touched by this path at all today, for any actor with real per-level history.
