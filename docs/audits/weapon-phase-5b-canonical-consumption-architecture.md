# Phase 5B — Canonical Weapon Consumption Architecture

**Rule:** every certified field must have an intentional consumer. *Every field is used* — not *every field affects damage*.
**Frozen:** Phase 3B mechanics and Phase 4H semantics/selectors/proficiency (203 identities). Nothing in them changed. No production weapon changed. No combat consumer is wired to the new runtime (a test enforces that nothing outside `scripts/items/weapon-runtime/` imports it).

## 2. Adversarial test of the 5A adapter design (5B-24)

The 5A `ResolvedWeapon` / `ResolvedAttackProfile` sketch was checked against all certified paths (2,187 after 5B-R). It **failed** in three places and was redesigned (this is the cheap point):

1. The first 5B registry (earlier in this phase) dropped `canonicalStats`-adjacent **`operation.*`** (≈250 bespoke structured mechanic keys), `summary`, `canonicalPlayerText`, `sourceClaims`, `firstPublication`, `sourceFootnotes`, `qualityAuthority`, `ambiguities` and the Phase 4H **`authorities[]`** (which holds the recommendation metadata: `recommendationFit`, `relativeTo*`, `rationale`). They are now carried by the registry and exposed on `ResolvedWeapon`.
2. `proficiencyRules`, `ontologyGapsAndUnrepresentedMechanics` and `authorityDiscrepancies` were not exposed; now exposed.
3. Only `crossPublication`, `repoComparison`, `mergeAudit` (and the superseded 4H `authorities[].semantic/source/proficiencyRoutes`) are intentionally **not** loaded at runtime; they are `VALIDATION_ONLY` with the audit tools as their consumer.

Resulting runtime model (implemented as the unwired foundation in `scripts/items/weapon-runtime/`):

```
ResolvedWeapon  (immutable, deep-frozen, references frozen registry data)
├── source: 'canonical' | 'legacy'        ├── identity {identityKey, canonicalName, via, productionId, registryHash}
├── weaponGroup, schemaFamily             ├── canonicalStats (size/cost/weight/availability/resource/ammo/stateMachine/…)
├── profiles[] (executable)               ├── defaultProfileId, selection {profileId,payloadId,configurationId,damageMode}
│   id,label,branch,subcategory,proficiencyGroup,exoticWeaponIdentity,matchedModes,definition(3B profile, all fields)
├── payloads[], configurationStates[], stateMachine
├── proficiency (4H) + proficiencyRules (3B)   ├── selectors, semanticTags, abilityInteractions
├── qualities, qualityParameters, conditionalQualities, conditionalDamageProfiles, operation
├── display {summary, canonicalPlayerText, sourceFootnotes}   ├── provenance {sourceClaims, firstPublication, ambiguities, …}
├── recommendation {categories, authorities}   ├── ontologyGaps, authorityDiscrepancies
├── ownedState (equipped/quantity/current ammo — mutable, never in registry)
└── diagnostics {profileDefinitionIncomplete, selectorOnlyModes, unmatchedPhase4HModes, heuristics:[]}
```
Facet resolvers (`resolveProficiency`, `resolveDamageProfile`, `resolveRange`, `resolveResource`) produce the per-profile views. Two limits remain and are listed honestly: `operation.*` mechanics are exposed as raw structured data (their executors are Phase 5E/5F work), and conditional modifiers/qualities need an evaluator that does not exist yet.

## 4. Player choices vs. never-edited data (5B-8)

Legitimate choices (all surfaced from resolver data, never as editable rules): equip, attack profile, melee/thrown, bayonet/ranged, stun vs lethal, payload, fire mode, configuration, one/two-handed where `wieldingRules` permit, target, combat options, damage type where `damageType.mode === 'or'` (`requiresDamageTypeSelection`).
Never edited by a player (the item sheet becomes read-only for canonical weapons): weapon group, native/alternate proficiency, dice, die size, damage type, range profile, Accurate/Inaccurate, rate of fire, capacity, weight, cost, reach, critical behaviour, area, tags, selectors, special effects, source. Boundary check: the only mutable things in the model are `ownedState`, selection, and the AttackWorkflowContext.

## 5. Consumption reviews (5B-9 … 5B-20)

* **Damage (5B-9).** `diceCount`/`dieSize`/`flatBonus` stay structured; `formula` is for roll/display only; die-step and extra-die effects consume the structured values. `damage.mode` (`dice/fixed/none/special/modifier/conditional/alternate-profiles/ammunition/inherited/varies-by-payload`) drives interpretation; no 1d6 default for `none`/`special`. AND → one component carrying all types; OR → one selected type; single → one; a separate component only when `damageComponents` models a distinct event. Transformation points: payload selection and damage mode in `resolveDamageProfile`; critical/condition modification in 5E; component → packet in 5D.
* **Physical (5B-10).** `size` → wielding/light-weapon (`isLightWeaponForActor`), `weightKg` → `EncumbranceEngine`, `reach` quality → threatened squares/AoO, `wieldingRules` → hands/dual-wield/grapple. Today these are read from legacy item fields and name heuristics (`weapon-branch-resolver`, encumbrance).
* **Economic (5B-11).** `costCredits`, `availability.restriction/rare`, `variantsBy*`, payload `costCredits/weightKg/availability` → store pricing/filters, chargen, equipment browser. No duplicate price table is required once production items are canonical (5G).
* **Proficiency (5B-12).** Native group, exact Exotic identity, species routes, ability/talent overrides, profile-specific proficiency and family-level substitutions (Kissai lanvarok) all resolve in `resolveProficiency`; `system.proficient` is ignored for canonical weapons (legacy only). Implant/Spacehound are explicit inputs, not inferred.
* **Range (5B-13).** Global band tables stay in `data/actor-weapon-ranges.json`; the weapon supplies `range.profileId`, `allowedBands`, `hardMaxSquares`, `penaltyApplication`, Accurate/Inaccurate, thrown, conditional rules.
* **Rate of fire (5B-14).** `rateOfFire` ∩ actor feats (Burst Fire/Autofire) gate the options `CombatOptionResolver` offers.
* **Resources (5B-15).** Canonical definition (`resource`, `ammo`, `resourceProfiles`, `resourceConsumption`) stays separate from owned current ammo / loaded payload / configuration (flags).
* **Special mechanics (5B-16).** See `weapon-phase-5b-special-mechanic-consumption.json` — 38 families, each with identities, current support, future consumer and phase.
* **Semantics (5B-17).** Tags/selectors/abilityInteractions feed applicability and recommendation only; the verifier test forbids any `semantic`/`categories` path from being classed EXECUTION. Stun behaviour comes from the structured `stun` model, never a `stun` tag.
* **Display/provenance (5B-18).** Full sheet: description, summary, qualities, source/page, notes. Compact row/store card: summary, price, availability, proficiency state. Tooltip: summary. Source panel: `sourceClaims`, `firstPublication`. GM/debug panel: ambiguities, precedence, diagnostics, hashes.
* **Recommendation (5B-19).** Data contract = `semantic.*`, `selectors`, `abilityInteractions`, `recommendation.authorities[].plannerMetadata` (`recommendationFit`, `relativeTo*`, rationale), plus `resolveProficiency` compatibility and actor abilities; exact ability/selector matches outrank tag similarity. No scoring implemented here.
* **Non-combat fields (5B-20).** Source page, publication precedence, ambiguities, recommendation prose, price, rarity, cross-publication history, repo comparison, merge audit are intentionally outside live combat (DISPLAY/STORE/RECOMMENDATION/VALIDATION).
