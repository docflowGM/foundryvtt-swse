## C3-R1 — Virtual-unarmed variants and actor provenance
**Defects (reproduced):** (a) `buildVirtualUnarmedWeapon(actor, { extraDamageDieSteps: 8 })` produced an enhanced strike that the gate accepted as genuine, because the builder applied unrestricted caller-supplied `extraDamageDieSteps`, `flagMarks` and `attackOptions` and then registered the result; (b) provenance was bound to `actor.uuid ?? actor.id`, so a distinct object sharing those strings passed the cross-actor check.
**Fix:**
* The builder no longer accepts bonuses, flag markers or attack options. A caller names a **variant** (`'slammer'` is the only one). Mechanics are decided inside the unarmed authority from the actor: the Slammer strike's Crush die-step is granted only when the actor has the enabled `Crush` feat or the stored `SLAMMER_SPECIAL_ATTACK` rule with `crushFeatAddsUnarmedDamageDie` — exactly the condition Slammer used before. Any other option (including the former three) is ignored.
* Eligibility is read through `scripts/engine/feats/grapple-rules-reader.js`, the four read-only feat / grapple-rule readers **moved unchanged** out of `grapple-feat-actions.js` so the unarmed authority does not import the actions module (which imports it). `grapple-feat-actions.js` imports them back; Slammer now calls `buildVirtualUnarmedWeapon(attacker, { variant: 'slammer' })` and supplies nothing.
* A requested droid appendage is honoured only when that appendage type is installed on the actor (previously any requested type chose the damage). No current caller passes `appendage`.
* Provenance records the **actor object** and requires `rec.actor === actor`. Same-id / same-uuid copies, `Object.create(actor)` stand-ins and stale instances are refused.
**Compatibility:** every in-repo caller (sheet, chat bridge, reaction registry, hotfixes, grapple, knock-heads, grapple damage) builds the strike from the same actor object it then attacks as; the full suite confirms no flow broke. A caller that builds from one actor object and attacks as another instance of the same document is refused by design.

## C3-R2 — Force Point transaction
**Defects (reproduced):** the readiness guard ran before the `PRE_FORCE_POINT` middleware, the roll, the spend and the chat message, so middleware (or the nested attack's own asynchronous steps) could invalidate the weapon after the point was spent; the attack was then refused with the Force Point gone and a "Force Point Used" message posted.
**Fix:** `SWSERoll.beginForcePointUse(actor, reason)` asks, runs the middleware and rolls the bonus but **spends and posts nothing**; it returns a transaction `{ result, commit(), rollback(), announce() }` built by the new dedicated module `scripts/combat/rolls/force-point-transaction.js` (so the transaction logic lives outside the `SWSERoll` facade, whose `phase2-legacy-facade-delegation` proximity guard it would otherwise erode). `commit()` is a success **only when the authority reports a point actually spent** (a throw, or a result of `spent < 1`, is a failure with nothing to refund) and spends through `ActorEngine.spendForcePoints` (the one authority; no second Force Point authority) and records **what that spend took** (the normal point(s) and, per bonus entry id, the bonus point(s)); `rollback()` gives back **exactly that and nothing else** — the normal point through `ActorEngine.gainForcePoints` (a relative gain, clamped to the maximum) and the bonus point added back to the *current* bonus pool by entry id. It never writes an absolute snapshot, so a Force Point regained, spent or granted by anything else since the commit is preserved (tests: a point regained during the spend yields 3 − 1 + 1 + 1 = 4, not an overwritten 3; a bonus grant arriving before the rollback survives; the rollback never exceeds the maximum). The transaction is **single-use and idempotent**: a second `rollback()` refunds nothing, a rolled-back transaction cannot be committed, announced or rolled back again, and a rollback that fails part-way does not repeat the half that succeeded. Tests also cover two interleaved transactions (only the rolled-back one's point returns). `announce()` posts the message and the POST hook, only for a committed, unfinished use.
* `attacks.js#rollAttack` takes the transaction as `forcePointTransaction` (kept out of the roll options so it is never serialized), commits it as the **last step before the dice**, after the final readiness check, and **re-checks readiness after the commit** (committing awaits); a refusal then gives the Force Point back (as above) together with the ammunition and action payments. A throw rolls it back with the other payments.
* `SWSERoll.rollAttack` and `rollAutofire` begin the transaction after the dialog and hook and announce it only once the attack was rolled with it. `rollFullAttack` commits when the first attack is about to be rolled, re-checks, and announces only if at least one attack used it; if the sequence ends before any attack, the spend is given back.
* `promptForcePointUse` (damage and skill checks) keeps its spend-then-announce behavior as a thin wrapper. The temporary `guard` parameter of WP5-C2 was removed.
**Feat matchers (finding, deliberately not changed):** the unarmed helper already had its own `actorHasFeat` (slug match including `system.slug`, no `disabled` check) for the Martial Arts steps; that is pre-existing and unchanged. Crush uses the grapple reader's matcher (normalized name, `disabled` honoured) — the one Slammer always used — imported under the explicit alias `actorHasGrappleFeat`. So no matcher was added, but the repo has two feat-name matchers with different semantics, now both visible in one file. Unifying them would change which feats count and is a separate decision; a test pins that the helper keeps exactly one local matcher and that Crush never goes through it.
**Test limit (honest):** the Force Point is only reachable from `rollAutofire` through the roll-modifiers dialog, which cannot be driven offline, so the autofire commit/rollback path is covered by the shared transaction tests and by code symmetry with `rollAttack`, not by a dedicated deterministic autofire test.

## C3-R3 — Truthful reload persistence
**Defects (reproduced):** `AmmoSystem.reloadWeapon` swallowed a failed `clearReload` and returned success (full pool, partial pool, and through `reloadBySecondCrew`, which kept the crew action while `needsReload` stayed true); and `FireStateStore` treated any resolved `ActorEngine.updateOwnedItems` call — including `[]` — as `persisted`.
**Fix:**
* **Update-result contract.** Foundry resolves an embedded-document update with the documents it actually changed. A write is `persisted` only when the result names the intended Item (`confirmsItemUpdate`). An unconfirmed result is `unchanged` only when the in-memory record already holds the requested state (a no-diff update), otherwise `failed`. The same check guards the ammunition write in `reloadWeapon` (`reason: 'ammunition-not-updated'`, unless the pool is demonstrably already full).
* **Two facts kept apart.** `reloadWeapon` reports the ammunition restoration and the clearing of `needsReload` separately. A failed state clear yields `{ success:false, reason:'reload-state-not-persisted', ammunitionRestored, reloadStateCleared:false }` — never an unqualified success.
* **No duplicate ammunition, no false readiness.** After a partial failure the pool is full and `needsReload` stays true, so previewReadiness keeps the weapon unfireable; the retry finds a full pool, writes no ammunition and only clears the state. `needsReload` is never set false in memory without a confirmed write.
* **Second crew.** `reloadBySecondCrew` already gives the crew action back on `reload.success === false`; it now actually fires for a failed state clear and reports `ammunitionRestored`.
* **Sheet reload gap closed — and the rollback itself made safe.** `ActionEconomyConsumption.spend` returns a rollback, but it called `Persistence.undoLast`, which pops *whatever history entry is last*: reproduced at `8fbd863`, rolling back spend A after spend B had been recorded undid **B's** swift action and left A in place. Every spend now stamps a unique `spendId` into its own history entry and its rollback proceeds only while that entry is still the last one; otherwise it changes nothing and reports `false`. The rollback now distinguishes and reports three outcomes as a strict boolean plus `handle.rollbackStatus`: **`refunded`** (this spend's entry was last, was undone, and is verifiably gone from the history), **`superseded`** (another action was recorded after it: nothing was changed, the later action is untouched and this one stays spent) and **`failed`** (the undo did not complete or did not remove this spend's entry). It never reports a refund the history does not show — including when `undoLast` itself claims success or returns `{ allowed:false }` (the earlier code returned `undoLast`'s truthy result object even for a refusal) — and a second call after `refunded` does nothing. Whenever the action stays spent the economy authority tells the player ("…could not be refunded automatically… Please correct the action tracker by hand"), so no caller proceeds silently as though the action were restored. This is a fix to the shared authority (attacks and FireStateStore benefit too; for them a superseded rollback now does nothing instead of undoing the wrong action). The sheet's reload spends through a new thin base-sheet method `_spendActionEconomy` (that authority, keeping the handle), gives its action back when the reload could not be recorded, and **tells the player when it could not be refunded** because another action was recorded since. Residual limit: the check-and-undo is atomic within one client only; a second client writing the same turn-state flag between them is not detectable here. The sheet's boolean `_applyActionEconomy` is untouched for every other caller.
* WP5-C1 field-scoped deltas and the concurrent-grip protection are unchanged (a test blocks the state write, changes the grip, releases, and checks the grip and unrelated fields survive and the write never names the grip). `commitFired` remains best-effort and reports its outcome.
**Test-mock correction:** 12 harness mocks of `ActorEngine.updateOwnedItems` mutated the Item but resolved with nothing, which Foundry never does. They now resolve with the changed documents (`updates.map(u => actor.items.get(u._id)).filter(Boolean)`). The sheet-reload test probes the new `_spendActionEconomy` instead of `_applyActionEconomy`; its assertions are unchanged.

## C3 follow-up — C3-R4 / C3-R5 / C3-R6 and the Force Point lifecycle (independent review of `961f4bc`)
**Defects (reproduced against `961f4bc` by `equipment-e4c1-wp5-c3b-force-point-lifecycle.test.mjs`, which runs the REAL `ActorEngine.spendForcePoints` / `gainForcePoints` over a controllable persistence layer):**
* **C3-R4** `announce()` had no once-only guard: two sequential or concurrent announcements posted two chat cards and ran the POST hook twice; `createChatMessage` resolves `null` (does not throw) on failure and was reported as announced.
* **C3-R5** two simultaneous `commit()` calls could both reach the spend authority (a second spend); concurrent `rollback()` calls could refund twice; a spend that applied and then threw was reported as a plain failure and could be repeated.
* **C3-R6** `SWSERoll.promptForcePointUse` returned `0` when `announce()` threw, although `commit()` had already deducted the point: a paid bonus was discarded.
**Fix (`force-point-transaction.js`, `enhanced-rolls.js#promptForcePointUse`; still no second Force Point authority — all pool writes remain `ActorEngine`):**
* `commit()` and `rollback()` are **single-flight**: simultaneous callers share one run and one outcome; a rollback requested during an in-flight commit waits for it. A commit that fails *cleanly* (pool unchanged) is retryable. A commit whose spend **threw after the pool visibly changed** is `state: 'indeterminate'`: closed, reported as `false` (never a fabricated success), never spent again and never refunded automatically (the player is told to check the pool).
* **Lifecycle decision (engineering, not a rule):** `announce()` (or `finalize()`) makes a completed use **final**: `rollback()` is refused afterwards, so a completed, mechanically applied use cannot be refunded by a later unrelated call and an optional presentation failure never reopens the payment. The refund path for an attack refused *before* completion (no announce yet) is unchanged. Finalization does not depend on the presentation succeeding.
* `announce()` is once-only **per step** (`chatPosted`, `hookRan`), concurrent calls share one run, it **never throws**, a `null` chat message counts as a failure, and a failure returns `false`, records `announceError` and warns the player that the point *was spent and applied*. A retry repeats only the failed step. Spend failure (`commit() === false`) and announcement failure (`announce() === false`, `committed === true`) are therefore distinguishable.
* `promptForcePointUse` returns `tx.result` after a successful commit regardless of the announcement outcome; it still returns `0` when the spend failed.
### C3-R7 — cross-operation interleaving (second independent review, `4517cee`)
**Defect (reproduced against `4517cee`):** same-operation single-flight did not protect *different* operations from each other. With a committed transaction and the refund write blocked, a `rollback()` started and not awaited left `committed:true, closed:false, final:false`, so `announce()`, `finalize()` and `commit()` all returned `true` (a posted "Force Point Used" card and POST hook for a point that was then refunded).
**Precedence rule (single client, decided synchronously — the first operation *accepted* wins):** `rollback()` is accepted only if the use is committed (or its commit is in flight) and not closed/final, and sets `rollbackAccepted` **before its first await**; from then on `commit()`, `announce()` and `finalize()` return `false` and have no side effect. Conversely `announce()`/`finalize()` set `final` synchronously, so a later `rollback()` is refused. A rollback that fails part-way keeps the claim (a half-refunded spend is never announced or finalized as a completed use) and may be retried; the claim lapses only if the commit it was waiting for failed (nothing was spent). No new authority, ledger or state machine beyond one flag.
**Tests:** `equipment-e4c1-wp5-c3b-force-point-lifecycle.test.mjs` check 6 (real `ActorEngine` spend/gain methods): refund blocked → unawaited `rollback()` → `announce()/finalize()/commit()` all `false`, no chat, no hook, balance 3 after release, one gain, state `rolled-back`; failed-then-retried rollback; rollback queued behind an in-flight commit; reverse ordering (announce/finalize first bars rollback).

**Existing-test change (deliberate):** `trust-boundaries` check 7d previously asserted that an *announced* transaction could still be rolled back (refund 3). Under the lifecycle decision above that refund is now refused, so the assertion became "rollback false, balance stays 2, gains [1]". No other existing assertion was changed.
**Limits (honest):** single-client guarantees only (Foundry has no compare-and-swap); "indeterminate" is detected by comparing the normal and bonus pool before/after, so a spend that threw after changing nothing observable is treated as a clean failure. Offline evidence only (L1/L2); not FOUNDRY_TESTED.
