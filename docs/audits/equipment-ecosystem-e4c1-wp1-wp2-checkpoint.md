## 2. WP2 — invariants and authoritative reader
**`scripts/engine/equipment/weapon-record-invariants.js`** (pure; imports only the E3-A4 posture vocabulary). API: `validateWeaponRecord(system, {knownAppendageIds?, requiredHands?})` → `{status: valid|absent|invalid, posture, occupancy, issues}` (posture/occupancy populated only when valid); `validateWeaponRecordTransition(before, after, {…, explicitRepair?})` → `{allowed, changed, from, to, issues}` (structural legality only: a malformed or absent target is never persisted, a malformed source is never silently replaced, repair/initialization must be explicit and is reported; action costs, grips and cross-Item conflicts stay with their authorities); `createDefaultWeaponRecord()`; `WeaponRecordInputError`. Enforced: contract §3.2 items 1–5 (STOWED⇔empty, EQUIPPED/READIED need purpose and appendages, READIED needs `wield`, distinct non-empty ids, optional anatomy membership and canonical required-hand count, schemaVersion 1 and exact shape). Retired fields are reported, never read as posture.

**`scripts/engine/equipment/equipment-state-reader.js`** (read only). API: `readActorEquipmentState(actor, deps)` and `readWeaponEffectivePosture(actor, itemId, deps)`. It reads each weapon's record, the FireStateStore record (grip choice), `system.activated` (independent activation evidence) and canonical weapon identity, then composes the existing resolvers: anatomy → species permissions → physical occupancy (cross-Item conflicts) → weapon grips → effective posture. Per weapon it reports `{record, pending, effective, status, effectivePosture, issues}`; the actor-level result adds anatomy, occupancy, grip, conflicts and a summary.
* A verified READIED needs the exact wield assignment, the canonical grip for that exact Item and resolved anatomy (E3-A5 rules); a missing grip choice, hold-only assignment, mismatched hand count, disabled/missing/unknown appendage, cross-Item conflict, non-canonical weapon or unsupplied species profile never certifies it.
* No hand is chosen, repaired or defaulted; invalid records never enter the occupancy resolver.
* Natural and integrated weapons stay pending (`indeterminate`, `effectivePosture: null`): flags and `system.integrated` can only withhold readiness, never grant it.
* Evidence adapters are injected (`resolveSpeciesProfile`, `getFunctionalOverrides`, `getInstalledComponents`; test seams `shapeOfWeapon`, `readFireState`). **Dependency found:** no synchronous actor → selected effective species profile adapter exists today (the profile is built asynchronously from the species registry); WP3+ must supply one. Until then the reader reports `species-profile-not-supplied` and the anatomy resolver's partial result keeps everything uncertified. The droid installed-component adapter is likewise deferred.
* `tests/weapon-runtime-builder-negative.test.mjs`: one allowlist line was added for the reader (it imports the canonical shape helper), as manifest guard 12 requires; no assertion was weakened.

## 4. WP3 execution design — evidence and recommendation (WP3 stays gated)
Findings are from repository evidence; Foundry v13 behavior not exercised offline is `RUNTIME_UNVERIFIED`. **Foundry v13 provides no suitable primitive** for: compare-and-swap or multi-document transactions, server-side validation of module data, or an authenticated sender on package socket messages. None is assumed below.

**4.1 Authenticated or constrained GM execution.** Repository evidence: `HolonetSocketService` registers `game.socket.on(NAME, payload => …)` and consumes no sender identity; its own comment records that the relay is not addressed to one connection (every active GM receives each request) and that `HolonetGmAuthority` cannot separate two tabs of one GM. The only server-enforced identity is document permission on writes. Recommendation: (a) do not treat `requesterUserId` as authentication; (b) at runtime verification time test whether a server-stamped document (for example a GM-whispered ChatMessage whose `author` the server sets) can carry the intent — if confirmed, the executor reads the authenticated author from the document; (c) if not confirmed, accept the interface as **asserted identity with a constrained blast radius**: the executor requires the named user to be connected and to hold OWNER permission on the actor, re-resolves every transition with the pure resolvers on fresh state (a forged request can only produce a legal transition of that actor's own weapon record and pay that actor's action), and records the asserted identity in the journal. The residual exposure — a connected player forging a request on behalf of another owner of an actor — is a security-policy decision for the project owner (an owner can already edit their own actor directly, so forgery adds exposure only across actors).

**4.2 Multi-GM and same-GM multi-tab.** `isPrimaryActiveGm()` resolves several GM users deterministically but not several tabs of one user. Recommendation: an executor lease — a GM-only world-setting record `{userId, sessionId, epoch, expiresAt}` claimed by the primary-GM client using the per-connection `game.sessionId` (not used anywhere in the repository; availability `RUNTIME_UNVERIFIED`), renewed on a heartbeat, re-read immediately before each protocol phase, and fenced by `epoch` written into the journal (4.4). A stale executor that loses the lease aborts with `LEASE_LOST`. Without compare-and-swap, lease hand-off keeps a short overlap window; this is reported as a limitation, not solved.

**4.3 Request id bound to an immutable intent digest.** `requestId` = random UUID from the requester; `intentDigest` = SHA-256 over canonical (sorted-key) JSON of `{schemaVersion, actorId, intentType, params, confirmations, basis}`. The executor stores `requestId → {digest, state}`; the same id with a different digest is `REQUEST_ID_CONFLICT` (rejected); the same id and digest returns the recorded state and never re-executes unless the classification is `NOT_APPLIED` (4.4). `crypto.subtle` exists only in secure contexts (a plain-http Foundry host has none) and `foundry.utils.hashCode` is a 32-bit non-cryptographic hash, so use a small in-repo pure SHA-256 verified against known test vectors.

**4.4 Durable duplicate and partial-commit classification.** One `lastRequestId` is not enough (a later request overwrites it, a multi-Item write can commit partially and the spend lives in another document). Recommendation: a bounded executor-owned journal in one field-scoped actor flag (`flags.swse.equipmentTxn`): per request `{requestId, intentDigest, epoch, phase: prepared|applied|finalized|compensating|aborted, items:[{id, beforeFingerprint, targetFingerprint}], spend:{marker}}`. Protocol: precheck affordability read-only → write `prepared` → write Item owned paths → verify → spend → write `finalized` with the verified outcome. A pure classifier compares each Item's current fingerprint with `before`/`target`: all target → `APPLIED`; all before → `NOT_APPLIED`; some of each → `PARTIAL`; anything else → `INDETERMINATE_CONCURRENT_CHANGE`; combined with the spend marker (4.5) it yields spend-mismatch variants. Only a `finalized` entry replays as success. Every other state is reported with its classification and resolved only by an explicit, confirmed reconcile plan; an uncertain transaction is never replayed as confirmed.

**4.5 Action-spend deduplication and reconciliation.** Evidence: `ActionEconomyPersistence.commitConsumption` stores the whole turn state in one actor flag and appends a history entry carrying the caller's `metadata`; `ActionEconomyConsumption.spend()` returns `rollback()` which calls `undoLast`, which **pops whatever history entry is last and restores its entire `before` turn state** — it is not tied to the caller's own spend, would undo a later consumption, and returns an object (truthy) even when there is no history. Therefore (a) the coordinator must not call `spend.rollback()` after any interleaving, and must verify the last history entry carries its own `requestId` and the turn state equals its `after` before ever using it; otherwise it reports `SPEND_NOT_ROLLED_BACK`; (b) pass `metadata.requestId` into the spend so deduplication is a history scan for that id; (c) order the protocol **spend last** (write → verify → spend → finalize) so that a failed write never needs a spend reversal, while a failed spend after a verified write is compensated by the conditional Item inverse patch; (d) a request-scoped reversal in the action-economy authority would be cleaner, but that is an action-economy change which this work does not authorize.

**4.6 Field-scoped compensation without unsafe overwrite.** Already specified in the contract §4.5 (owned paths only, restore a path only if it still holds the planned value, leave and report anything else). Foundry offers no conditional update, and module hooks such as `preUpdateItem` run only on the writing client, so they cannot fence a remote writer: the read-compare-write window is irreducible. A race there yields `FAILED_PARTIAL` or an uncertain status, never `FAILED_COMPENSATED`.

**4.7 Honest handling when completion cannot be established.** Timeout, relay loss, executor death or a lost lease yield `UNKNOWN_OUTCOME`; the requester calls a reconcile request (same `requestId`) which classifies from the journal (4.4). An unreadable or missing journal yields `INDETERMINATE`, surfaced to the player/GM with the evidence. The mutation is never retried automatically; a retry with the same digest is permitted only from `NOT_APPLIED` with no spend marker.

**Decisions needed before WP3 can be authorized (all engineering-vs-policy boundaries; none changes a game rule):**
1. Identity: verify the server-stamped-document route at runtime, or accept asserted identity with the 4.1(c) blast radius.
2. Action economy: accept the spend-last protocol with no spend reversal (recommended), or separately authorize a request-scoped reversal in `ActionEconomyPersistence`.
3. Accept the lease-plus-epoch model and its documented hand-off window.
4. Authorize an in-repo pure SHA-256 helper (with test vectors) for the intent digest.
