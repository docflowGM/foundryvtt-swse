**Owner's clarified intent:** Galactic Profiles are **fast characters**, designed to bypass *already-resolved* work, not the canonical V2 legality gates. Templates should carry class, species/version, attributes, skills, feats, talents, items, and net remaining credits and proceed only to genuinely unresolved choices. **Equipment and remaining credits are ASSUMED economically legal** (the gear is treated as already purchased from starting funds); do **not** reopen price/wealth or equipment-shopping arithmetic. Audit only correct **delivery/materialization** of the listed gear and net credits.  
**Talent policy:** Default RAW (Talent Wiki OFF): character receives talent(s) only from the *advancing class's own progression table*, at level 1 normally **one class-granted talent** for a heroic base class and **no general/heroic bonus talent**. A class talent may be drawn from the class's allowed trees or an eligible Force tree if Force-sensitive (Core p. 100), subject to prerequisites. Optional GM house rule `talentWiki` ON: independently grants an additional heroic/general talent at heroic character level 1 (plus class talent), with house-rule modifiers gated behind Talent Wiki. The word **general** here refers to the **source of the entitlement**, NOT an intrinsic category of published talent. Where two different legal talents in a template form a prerequisite chain, allocate the prerequisite to the class slot and the dependent talent to the optional general slot, and test the acquisition order. Never turn two duplicate representations of the same talent into two grants. More than two is not automatically legal. The generated character must be valid with Talent Wiki OFF.

## E. Other rules gates still requiring template-by-template proof

- **Starting class feats:** distinguish free starting feats from 1st-level general choice and human/species extra choice. - **Species:** identify publication/version, ability modifiers, conditional grants, languages, trained skill modifications, trait applications. Adapter correctly detects an unresolved multi-publication choice but incorrectly locks Species in that case.
- **Attributes:** validate a legal allocation/method and species adjustments, not only a 3–18 range.
- **Force:** `Force Training` feat eligibility, known power count = canonical applicable Force Training entitlement(s), selected Force powers' exact IDs, and legal class access. A Jedi class label is **not** the correct general rule for Force powers; use Force Sensitivity, Use the Force training and the feat's published rules.
- **Background:** template background identity and class/species interaction must use background ledger when enabled; current validator is only a placeholder.
- **Equipment and credits:** **assumed RAW-compliant as supplied, no shopping-price retest**. Test only that selected gear and net credits are present on finalized actor and not charged a second time.

## Checkpoint 2 — Galactic Profile JSON/schema and application architecture review (2026-11-16)

**Scope:** Design/read-only review of pinned repository source; no repo changes, no approvals implied. This supplements, rather than supersedes, checkpoints 1/1A. User wants fast, playable Level-1 characters; equipment prices and starting-funds shopping math remain ASSUMED legal, only exact delivery of kit/net credits is tested.

### Newly substantiated findings

- **GP-020 — P0/P1, credit amount semantic mismatch (CONFIRMED CODE):** `data/character-templates.json` supplies `credits` as net **remaining** cash, including valid `credits: 0` templates. `template-adapter.js:137-275` never conveys that amount into the canonical draft; `progression-finalizer.js:944-947` expects `survey.startingCreditsResolved` or positive `survey.startingCredits`, and `:1512-1522` uses a positive explicit `startingCredits` as a budget, otherwise computes class/background starting budget plus potentially Wealth. `:2674-2687` defers to chargen store state when initialized. **Required:** a distinct final-balance credit semantic for a pre-purchased, pre-equipped profile, including zero, that cannot be recomputed, wealth-added, re-spent or overwritten by store logic. Avoid shoehorning net cash into `startingCredits` without modifying its meaning explicitly.
- **GP-021 — P1, class starter equipment collision (CONFIRMED CODE, future collision risk if profile kit is added):** `progression-finalizer.js:1783-1790,3057-3110` auto-grants a Jedi starter lightsaber when the live actor lacks one, but the existing Jedi Galactic Profiles also list a lightsaber as template kit. If kit materialization is added independently without a planned-manifest dedupe, both can be granted. **Required:** resolve class/species auto-equipment and profile loadout into a unified item-grant plan, collapsing overlap by canonical item identity and grant provenance before mutation. Do not remove the class starter rule globally.
- **GP-022 — P2, opaque skill IDs shown as card labels (CONFIRMED CODE):** `galactic-profile-step.js:89-97,281-310` derives `skillsPreview` through `itemName`, which displays an item's `name` field; heroic JSON stores many `trainedSkills` objects with `name` equal to a 16-character opaque ID, e.g. `jedi_guardian` `2b9e43f710664b31`. **Required:** resolve canonical skill names for card/review render via a display projection, never trust `name` or `displayName` fields inside template JSON as identity.
- **GP-023 — P1, superficial registry validation and mixed schema versions (CONFIRMED CODE):** `template-registry.js:135-219,225-320` accepts root version 2 for heroic, independently concatenates root version 1 nonheroic, validates mostly field existence, only logs invalid rows, uses linear lookup, and treats nonheroic JSON load failure as nonfatal even for a route requesting such templates. **Required:** versioned JSON Schema, unique ID enforcement, subtype-specific validation, referential integrity against canonical V2 data, and failure/retry statuses. `Map` lookup is a cleanup, not the primary performance bottleneck at 33 records.
- **GP-024 — P2/P3, duplicate pure compilation and denormalized mechanics in UI (CONFIRMED CODE):** `galactic-profile-step.js:250-270,561-579` constructs two previews per Review read; `formatTemplateForCard`/`formatTemplateReview` display raw pre-reconciled JSON instead of canonical display projections. Some JSON notes contain hardcoded Attack/Reflex/HP snapshots, which are liable to diverge from V2 computed stats. **Required:** one compiler output reused for review, outstanding-choice computation and apply, with mechanical projections calculated once; treat text-only copy and dialogue as non-authoritative.

### Architecture decision proposed for owner approval

**Keep JSON as the profile authoring format**; no parallel character engine, no direct raw Actor writes from templates. Implement schema v3 via a clean cutover (not permanent shims/crosswalks):

1. **Catalog/presentation layer:** stable profile ID and revision, name/class/category, role/search tags, images, mentor/dialogue key, short card description, eligibility and catalog order. Generate a compact production catalog from authoring records; avoid manually duplicating title/class/tags in multiple data files.
2. **Mechanical manifest layer:** explicit `participantKind` and `rulesTrack` (`heroic` versus `nonheroic`/beast/droid as supported), level, canonical V2 content references with stable IDs and publication variant, unambiguous attribute base-vs-final semantics, trained skill IDs, feat grant/selection slots, talent entitlement slots, Force Training and powers, granted vs selectable languages, starting equipment list with quantity, and `remainingCredits` **finalBalance**. Keep published tree membership sourced from canonical talent DB, not independent hand-authored tree assertions.
3. **Source/eligibility layer:** source references and proof/certification metadata, optional GM-rule conditions (e.g. only one additional distinct general-talent entitlement if `talentWiki` ON), precise requires/preconditions, unfilled choice debt if any. Do not represent confidence as manually set `supportLevel: FULL`; generate certified status in checks.
4. **Compile-once planning service:** `GalacticProfileCompiler.compile(profile, { actor, rules, authoritativeRegistries })` returns an immutable `{sessionDraft, grants, netCredits, missingChoices, validation, displayPreview, provenance}`. All V2 domain validators own legal slot and prereq checks. No actor mutation at compile/preview time. A fully legal profile must have zero actionable debt when baseline rules are active.
5. **Atomic commit/application:** the deliberate Apply action (not Back/Close/onStepExit) uses a validated compiled plan, assigns session once, refreshes active steps once, and persists once. Reject unresolved blocking or invalid selections; optional choices remain open. Normal V2 finalizer emits a single mutation plan and applies equipment/net credits *once*.
6. **Efficient registry:** `Promise` de-duplication during load with `finally`/catch reset on failure, ID map and indexed facets after load, single preview cache keyed by profile revision + relevant house rules / authority digest / actor context, and intentional splash warmup. No per-card compendium fetches; preload compact index, batch authoritative resolves as needed. At only 33 profiles, creating dozens of network fetches would be a regression.
7. **CI certification:** JSON Schema and unique-ID/type checks, canonical ID and species publication proof, class/skill/feat/talent/Force prerequisites and quantities, both Talent Wiki OFF and ON, starting item/credit reconciliation, no duplicate class/species grants, and build/preview/final actor parity. Flag draft/unverified builds separately, do not offer them as silently `FULL` ready-to-play templates.

**Recommended file approach:** source-of-truth authoring modules (one per class or profile for easier editorial QA) -> generated `galactic-profiles.catalog.json` (lightweight card data) and `galactic-profiles.manifest.json` (mechanical data). For current 33 records, a **single consolidated, generated manifest** is perfectly reasonable; splitting into 33 HTTP files is unnecessary. Keep mentor dialogue in its dedicated data authority and link it by stable `dialogueKey` rather than fragile runtime guesswork. Preserve all 33 source IDs where possible, but create fresh revisions and certify content; no old schema compatibility layer after clean cutover.

### Proposed required invariant / acceptance contracts

- **One identity:** `profileId + profileRevision` maps to precisely one canonical loadout; subtype/heroic status cannot be inferred from class display strings.
- **One mechanical authority:** all canonical content references resolve by V2 registry ID plus publication/variant; human display names cannot change selection identity or prevent same-name talent differentiation.
- **One entitlement ledger:** class/species auto-grants are generated by V2; template selections occupy legal class/general/species feat and talent slots, never confer extra slots merely by having an array entry.
- **One lock contract:** lock step only when its *canonical required entitlements* are fully resolved, prerequisites pass and no required variant or choice debt exists; never lock because an array is nonempty.
- **One equipment/credits contract:** exact selected loadout is on final actor, once; `remainingCredits` equals supplied net balance, including zero; automatic starter items deduped against loadout; never charge again.
- **One navigation contract:** preview/Back/Close are read-only w.r.t. applied build; Apply commits once; no state reset/rebuild race; Finalize only once via V2.
- **One gameplay contract:** when a profile is shown as ready-to-play it must finish to a RAW-legal Level-1 character without further mechanical prompts under default settings; any intentional open choices are explicitly disclosed before selection.

**Priority order:** P0 establish schema and certify all 23 heroic profiles and subtype routing; P1 compiler/preview, atomic commit, class auto-grants/kit/net credits and locks; P2 UI accessibility, catalog card projections, search/filter; P3 cache/performance and Foundry v13 end-to-end tests. Roll out behind controlled V2 route and do not replace old production behavior without acceptance tests; this is a deliberate cutover, not a migration shim.

**Owner decision requested before coding:** approve JSON v3 + a single ProfileCompiler + generated catalog/manifest with strict canonical V2 application, or prefer a narrower incremental refactor. No implementation made by this document.

## Checkpoint 3 — Droid Galactic Profiles feasibility and architecture (2026-11-16)

**Scope:** Read-only architecture review against same pinned repo HEAD and the attached OCR of *Saga Edition Core Rulebook* (droid heroes) and *Scavenger's Guide to Droids* (Creating Droid Heroes, pp. 10–13). This is a recommendation, not a code change or completed RAW certification.

### Confirmed existing-code findings

- **GP-025 — P0, droid profile selection includes non-droid biological presets (CONFIRMED):** `intro-step.js:863–915` handles `[data-role="droid-select-standard"]` by calling `TemplateInitializer.initializeForChargen(actor, {subtype:'droid'})`. `template-initializer.js:97–129` uses the legacy modal and `TemplateRegistry`, not the new Galactic Profile three-step rail. `template-selection-dialog.js:333–351` filters `droid` entries by absence of `force/jedi/sith` in `t.classId.id`, without requiring droid subtype, droid rules track, or a valid chassis. All four existing Jedi records have opaque class ID `fec1f8af44fcc35a`, so the textual exclusion does not exclude them. Reproducing that exact filter against archived 33-source entries returns **28 profiles: 23 organic heroic (including four Jedi) plus five unflagged Nonheroic**; there are **zero** genuine droid-source profiles. `TemplateAdapter` droid payload only supports `droidId`/`droid` metadata, not a verified complete hardware build. Do not publish this picker as functional droid Galactic Profiles. Proposed gate: explicit `participantKind:'droid'`, `rulesTrack:'heroic-droid'`, and compilation through V2 droid eligibility/prerequisite authority.
- **GP-026 — P0/P1, stock-statblock vs playable-derived mode split is a hard boundary:** `stock-droid-importer-engine.js` imports published totals into `system.droidCalculationMode='stock-statblock'`. `droid-mode-adapter.js` and `docs/audits/droid-stock-statblock-authority-phase-3.md` preserve published totals without reapplying droid component modifiers. `droid-initial-installation-service.js` explicitly refuses installation ledger seeding for stock-statblock actors because it would double-count factory systems. - **GP-027 — P1, qualified status labels:** `data/store/stock-droid-certification.json` counts 194/194 `certified`, but its own schema explicitly limits this to source identity and importer acceptance, with `mechanicalCertification: 'NOT_PERFORMED'`. Source-only canonical droid entries must carry independent playable-eligibility and build certification before listing as quickstart PC profiles.
- **GP-028 — P1, hardware and financing require their own ledger:** `droid-builder-step.js:70–240,260–288` models droid `creationMode` (custom/standard-model), degree, size, locomotion, processor, appendages, accessories, `droidCredits.{base,spent,remaining}`, standard-model cost cap, and build-state lifecycle. `droid-initial-installation-service.js:1–12,109–118` compiles *finalized* hardware into `system.installedSystems` inside the single chargen mutation without charging again. A profile must supply an accepted completed droid builder selection, not just display names, synthetic on-actor system flags, or a second pricing engine. Keep *droid construction allowance* separate from class starting credits and final net spendable wallet. Core custom-droid rules provide the special 1,000-credit allowance; SGD stock-model 5,000-credit cap and chassis bonus systems have different semantics.

### Published options and launch recommendation

*Scavenger's Guide to Droids*, Creating Droid Heroes pp. 10–13, explicitly lays out **three** PC creation methods: (1) custom-built droid from scratch; (2) published standard model, subject to PC eligibility and a model/equipment cost cap; (3) stock droid chassis (species-equivalent chassis traits, bonus systems, class starting funds). The chassis table lists eight chassis across five droid degrees: medical, astromech, mechanic, protocol, service, battle, probe, labor. The Core droid hero section states no Constitution score, class choices Noble/Scoundrel/Scout/Soldier (not Jedi), and special degree/size rules; stock-model eligibility is narrower than the whole compendium. Read PDF page images for any disputed model-specific RAW certification.

**Decision proposed:** Add Droid Galactic Profiles, but distinguish **heroic ready-to-play droid builds** from **published stock-model imports**. Reuse the same profile catalog, class/role browsing, mentor presentation and ProfileCompiler architecture; give `participantKind:'droid'` its own normalized `build.droid` submanifest (method, degree, size, optional chassis, complete systems/components with counts/instance identities, grant provenance, build completion, separate construction budget, final wallet). Compiler must use `DROID_DEGREE_PACKAGES`, `DROID_SIZE_PACKAGES`, existing droid quote acceptance, the existing finalizer and `requireInitialDroidInstallation`, while obeying no-Con/no-Force/no-Jedi/class-feat/talent entitlement rules. Do not force `speciesRef` for a droid chassis (it is species-*equivalent* rules, not biological species data). Do not treat `actor.type` alone as an identity gate; the rules profile covers NPC droid followers too.

**Practical rollout:** Phase D0 fix/hide the misleading existing droid-profile button until supported. Phase D1 curate 4–8 level-1 heroic quickstart profiles using the existing **custom** droid mode and validated, preselected complete builder state (start e.g. Astromech Tech, Security Unit, Protocol Envoy, Medical Assistant, Probe Scout, Labor Salvager); this is the lowest integration risk. Phase D2 implement the optional actual SGD **stock-chassis** authoring method, with chassis-granted systems distinguished from custom free components; then expand toward all eight chassis types. Phase D3 separately expose only source-qualified **published stock-model imports** (or eligible standard-model-to-hero builds) behind their own importer/eligibility gate, rather than incorrectly labeling all 194 import-accepted records as mechanically certified playable heroes. Follower/Garage/store are later, separate consumers, not phase-one requirements.

**Hard acceptance requirements:** eligible class/degree/size/model; 5 ability scores + null/absent CON; no Force Sensitivity or Force powers; exact V2 class feats, talent entitlement count and prerequisites including Talent Wiki; installed hardware once with real ledger provenance; separate prepaid droid construction allowance and exact net spendable credits; no double-counting stock bonuses; no duplicate arms/locomotion/processor; atomic deliberate Apply, Back/Close read-only, accurate preview vs final actor; no effects on organic Galactic Profiles, existing custom droid creation, stock model importer or conversion service.
