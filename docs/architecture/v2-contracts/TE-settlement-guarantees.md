# TransactionEngine settlement guarantees (3N-TE.6) — what the code actually guarantees

Derived by reading `scripts/engine/store/transaction-engine.js` (+ `transaction-recovery.js`, `transaction-helpers.js`) at the 3N-TE.5 state. This documents **real** guarantees only; nothing here claims atomicity Foundry does not provide. Foundry has no multi-document transaction and no cross-client lock.

## Guarantees that hold (same client, offline-tested)
- **One in-flight operation per lock key.** `_mutationLocks` is an in-memory `Set` on the engine (per client). A second request with the same key is refused (`… already in progress`) with no second debit. Lock keys: `executeMutationTransaction` `actorId:context`; `executeCreditAdjustment` `actorId:context:credit-adjustment`; `executeAssetCustomizationTransaction` `walletId:assetId:context`; `executeAssetApprovalTransaction` `assetApprovalLockKey(owner, asset, context)` (shared with denials); `executeSaleTransaction` `actorId:context:sale:itemId`; `executeAssetSaleTransaction` `ownerId:context:asset:assetId`; `reconcileAssetSale` `reconcile-asset:assetId`; `executeRollbackCorrection` `actorId:store-rollback-reconciliation`. Locks are released in `finally`, including after indeterminate outcomes.
- **Credit-reconciliation guard.** While `_creditReconciliations` holds an actor, new operations on it are refused ("being reconciled"); `compensateUnverified` takes it for its read-compare-restore.
- **Recovery is a precondition, not best effort.** Mutation, credit-adjustment, customization, approval, sale and transfer paths establish a full-actor v2 snapshot (`establishRecovery`: created AND retrievable) before mutating; if that cannot be established the operation is refused with nothing changed.
- **Honest outcomes.** A result is exactly one of: success; definitive failure (nothing written, or written and VERIFIED restored); `rolledBack:true` (only after `restoreVerified` returned `true` and any created world actors were verified absent); `compensated` (targeted refund by read-compare-restore after an unverified change); `indeterminate` (+ `rollbackFailed` / `partialMutationPossible` / evidence) when restore or cleanup could not be verified. An indeterminate outcome is never retried by the engine and never reported as an ordinary failure.
- **Whole-actor restore is the existing mechanism** (SnapshotManager); it can revert unrelated concurrent changes made between snapshot and restore (documented TX-07b). Targeted recovery exists only for the unverified-charge case (`compensateUnverified`).
- **Completion hooks are presentation.** `emitCommitted` runs after commit; a throwing listener yields `presentationError` and never undoes the transaction.
- **Source-rollback replay is refused** (`sourceRollbackRefusal`): invalid id, not found, malformed record, or already rolled back (first rollback id preserved).

## Guarantees that do NOT hold (do not rely on them)
- No cross-client exclusion: two GMs/clients can run the same operation concurrently; the lock is per-process memory. The originating-client gating on hooks reduces duplicate reactions but is not a lock.
- No atomicity across documents: a transfer between two actors, or a wallet plus an owned asset, is a sequence of writes with verified compensation, not a transaction. The engine never claims otherwise; a failed compensation is `indeterminate`.
- A resolved `delete`/`update` call is not proof of persistence; verification reads state afterwards, and an unreadable registry is `indeterminate`.
- Nothing here is FOUNDRY_TESTED; live multi-client behavior is a separate acceptance requirement.

## Open design questions for later TE steps (no owner decision needed unless stated)
- TE.4 shared lifecycle: the eight `execute*` methods repeat guard → lock → snapshot precondition → apply → verify → commit-hook → restore/compensate, but each carries bespoke messages and result shapes that tests pin. A shared coordinator must be introduced behind differential tests per method, not by rewriting the flows.
